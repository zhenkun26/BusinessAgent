## 二、按评审五阶段排期映射的优化方向

### 阶段一：需求冻结、数据/权限梳理、架构评审（评审建议 2-3 周）

- 现状：系统边界、SLA、风险操作清单散落在产品文档与 README，无正式规格。
- 方向：新增主规格 `production-readiness`，把系统边界、SLA 指标（可用性/延迟/恢复时间）、
  风险操作清单（删除、外部发送、批量变更等需审批/审计的操作全集）落成正式规格并评审冻结。

### 阶段二：真实 CRM/邮件/工单/SSO 集成（评审建议 6-10 周）

- 现状：`external-system-integration` 规格与 `_call_external`/`http_adapter.py` 契约已就绪，
  是五个阶段中**基础最好**的一项。
- 方向：逐个系统推进真实接入（建议顺序：工单 → CRM → 邮件 → SSO），每个系统补齐
  幂等键、重试策略、Saga 补偿、审计回写、联调验收用例；Mock 保留为降级回退通道。

### 阶段三：工程化与安全补强（评审建议 4-6 周）

- 现状：58 用例回归套件 + CI 已就绪（评审差距 2 已补齐）。
- 方向：在此之上补三块——密钥管理（现状仅环境变量，评审要求密钥管理系统）、
  漏洞扫描（依赖与镜像扫描接入 CI）、权限与越权测试（横向越权用例）；
  顺带收口 ISSUES I-06（checkpoint 无 TTL）、I-07（token usage 部分采集）。

### 阶段四：性能、高可用、灾备与可观测性（评审建议 4-6 周）

- 现状：单机 Compose + 一次性并发冒烟，无正式压测、无演练、无告警值班。
- 方向：执行正式阶梯压测（vegeta/k6，定 p95/p99 与错误率门槛，收口 I-01）；
  备份恢复演练（pg_dump + etcd snapshot 做一次真实恢复并记录 RTO/RPO）；
  告警规则与值班预案；评估 K8s 启用时点（DEPLOY.md:418-433 已有判断标准）。

### 阶段五：UAT、灰度、稳定性观察（评审建议 4-6 周）

- 现状：I-02 open，无真实用户验收。
- 方向：定义并执行上线门槛——核心场景自动化回归全绿、压测达标、P0/P1 清零、
  权限与渗透测试通过、备份恢复演练成功、2-4 周灰度稳定运行。

### 贯穿项：RAG 答案质量

- 现状：检索满分但答案关键词覆盖率 0.606，22 条评测集规模太小，不能证明真实知识库下的准确性。
- 方向：扩充评测集（目标 ≥100 条，覆盖多业务域与对抗性问题）、定位低覆盖样本的失效模式
  （检索对但生成漏关键词 → prompt/上下文组装问题）、将覆盖率目标值写入 `knowledge-operations` 规格。

## 三、候选 openspec change 清单（供 propose 阶段挑选）

按"风险低 → 价值高 → 依赖少"排序，建议逐个 propose，不要打包成一个大 change：

| 优先级 | 候选 change | 范围 | 对应规格 | 对应评审阶段 |
|---|---|---|---|---|
| P0 | `production-readiness-baseline` | 系统边界/SLA/风险操作清单落规格 + 架构评审结论入 DECISIONS | 新增 `production-readiness` | 阶段一 |
| P0 | `rag-answer-quality` | 评测集扩充至 ≥100 条 + 低覆盖样本失效分析 + 覆盖率目标入规格 | `knowledge-operations` | 贯穿项 |
| P1 | `load-test-and-dr-drill` | 正式阶梯压测（vegeta/k6）+ 备份恢复演练 + 告警预案 | `quality-testing` 扩展或新规格 | 阶段四 |
| P1 | `security-hardening-plus` | 密钥管理、CI 漏洞扫描、越权测试；收口 I-06/I-07 | `user-lifecycle`/`quality-testing` | 阶段三 |
| P2 | `ticket-system-integration` | 首个真实外部系统接入（工单），幂等/补偿/审计/联调全链路 | `external-system-integration` | 阶段二 |
| P2 | `crm-mail-sso-integration` | CRM、邮件、SSO 真实接入（在工单接入验证模式后跟进） | `external-system-integration` | 阶段二 |
| P3 | `uat-and-ga-rollout` | UAT 计划、灰度方案、上线门槛检查单 | `production-readiness` | 阶段五 |

说明：阶段二的集成工作量最大且最不确定（评审原话），放在 P2 是为了先用 P0/P1 把
"上线门槛的度量能力"（SLA、压测、演练）建好，避免真实系统接完后仍无法证明达标。
