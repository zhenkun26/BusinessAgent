# DECISIONS · 设计决策记录

> 决策记录的单一事实源。格式：背景 → 决策 → 放弃了什么 → 改判条件。
> 内容从产品文档第十章与 Agent 项目面试备稿提炼，新增决策追加不改写。

## 1. LangGraph 显式状态机，而非 ReAct 自由循环 / AutoGen

- **背景**：企业场景要求路由可预测、权限决策点可审计、状态可恢复。
- **决策**：StateGraph 显式建模 planner → fan-out → aggregator，路由是代码而非 LLM 即兴决策。
- **放弃**：ReAct 应对完全未知任务的开放性、AutoGen 的多 Agent 自由对话。
- **改判条件**：开放任务占比显著上升时，在 executor 内嵌受限 ReAct 子循环，不推翻主图。

## 2. Supervisor 集中决策（单一 planner），而非去中心化路由

- **背景**：RBAC 与审计的落点需要集中。
- **决策**：planner 统一做意图分类 + 任务分解，executor 只执行。
- **代价**：planner 是决策单点；用超短消息短路 + 本地闲聊预判 + 云端运行时回退 + 规则降级四层缓解。
- **改判条件**：出现「意图分类覆盖不了」的开放式任务域。

## 3. 拆三个子 Agent（Knowledge/Analysis/Execution），而非单 Agent + 工具

- **背景**：三类任务的上下文构造、权限模型、失败语义差异极大。
- **决策**：独立 Agent + 统一 AgentResult 契约，可独立评测、独立换模型。
- **代价**：多结果需一次 primary LLM 汇总；用「单结果直通不调 LLM」压回成本。

## 4. Mock-first 工具策略，契约完全对齐真实 API

- **背景**：真实业务系统缺位，但安全链路（RBAC/Saga/审批）必须提前验证。
- **决策**：工具 Mock 实现 + pydantic schema/补偿语义对齐真实契约，`_call_external` 预留切换点。
- **放弃**：Mock 测不出真实系统的脏数据与延迟分布。
- **改判条件**：真实系统 API 契约冻结即切换（见 complete-business-processes 外部系统接入）。

## 5. 全栈降级链 + 降级必须可观测

- **背景**：任一依赖故障不宕机；但降级会掩盖配置错误（真实踩坑：memory 后端掩盖向量检索未生效）。
- **决策**：LLM/检索/Checkpointer 三条降级链；`/ready` 与响应暴露当前生效后端。
- **原则**：降级兜底可用性，不兜底可观测性——每条降级链必须配「我在降级」的信号。

## 6. Saga 补偿失败不阻断流程

- **背景**：分布式场景没有真正的回滚（邮件发出只能发撤回信）。
- **决策**：补偿失败记录 `compensation_errors` 继续返回，运维介入。
- **原则**：最终一致性 + 可观测 > 虚假的强一致。

## 7. 审批后按发起人角色终审（批准不越权）

- **背景**：审批系统不能成为提权通道。
- **决策**：经理批准后，工具仍按发起人角色过 RBAC（执行前显式预检 + 工具层终审），审计分离记录 decided_by 与 executed_as_*。
- **放弃**：审批人代办下属操作的便利性。

## 8. 本地小模型承担高频简单任务，云端只留给推理

- **背景**：云端成本与数据不出内网诉求。
- **决策**：闲聊判断/自评/意图分类/计划解析走本地 qwen3.5:4b；任务分解/分析报告/多结果汇总走 deepseek-v4-pro。
- **例外**：execution 工具选择云端 flash 优先（本地 4B 会选错工具，实测）。
- **原则**：按任务的最小能力需求配模型。

## 9. 拒答优于编造；数字永远来自 Python 聚合

- **背景**：企业知识库给错误制度答案的代价远高于「不知道」。
- **决策**：低置信度明确拒答；分析数字由 Python 真实聚合，LLM 只负责表达。

## 10. agent_results 用可重置 reducer

- **背景**：标准 `operator.add` 在断点恢复后会把上一轮结果追加进新一轮。
- **决策**：`_resettable_add`——右值为空列表即重置，非空即累加，一个 reducer 兼顾两种语义。

## 11. 文档六大层分类 + 单一事实源（2026-08-04 新增）

- **背景**：根目录 36 个 md 散落，进度/决策/坑记录多处重叠，无版本历史。
- **决策**：`docs/` 六大层（产品方案/产品文档/操作手册/过程记录/工程文档/知识数据库）+ 归档层；ROADMAP/ISSUES/DECISIONS 各为单一事实源；`interview/` 独立承载面试与演示资产；Git 全程版本控制。
- **放弃**：保持根目录散文档的「所见即所得」。
- **改判条件**：文档规模大到单层 README 索引不足时，引入文档站点生成器。

## 12. 上线契约冻结：边界 / SLA / 风险操作清单（2026-08-05，change production-readiness-baseline）

- **背景**：按真实企业上线标准，压测达标、UAT 验收与灰度放行缺少可引用的顶层契约，三类决策依据散落在产品文档与 README。
- **决策**：系统边界、SLA 指标体系（可用性 ≥99.5%、p95 ≤2s、p99 ≤5s、错误率 <0.5%、RTO ≤1h、RPO ≤24h，均为单机 Compose 现实初值）、风险操作清单（8 项，含批量判定标准 >1 条记录）冻结为 `production-readiness` 规格；盘点事实与草案全文见 `docs/40-process/上线评审材料-2026-08-05.md`。
- **放弃**：对标互联网 99.9% 可用性（单机架构无法兑现）；把审批流转细节并入本规格（违反单一事实源，留 approval-lifecycle）。
- **改判条件**：`load-test-and-dr-drill` 压测与恢复演练后必须回访校准 SLA；启用 K8s 后复评可用性目标。
- **备注**：本轮评审为 AI 自审（逐项对照代码与配置核实），待项目责任人最终确认。

## 13. RAG 低覆盖样本归因：先修关键词口径，再谈 prompt（2026-08-05，change rag-answer-quality）

- **背景**：22 条评测集检索层指标满分但关键词覆盖率仅 0.606。引入答案层评测（`eval/run_eval.py` 扩展，expected_keywords 在最终答案中的覆盖率）后实测：答案层覆盖率与检索层覆盖率逐样本完全一致，15 条低覆盖样本机械分类均为 assembly_omission。
- **归因结论**（逐条人工抽查 `eval/results/baseline_22_answer_small.json` 的上下文与答案）：15 条中 14 条为**关键词口径误伤**——markdown 加粗使数字/英文两侧带空格（文档写「24 小时」「90 天」，旧关键词写「24小时」「90天」），答案其实逐字含事实且内容正确；仅 Q007 为真实上下文组装遗漏（正确 chunk 未进 Top-5，模型按 prompt 规则如实答「未覆盖」，属生成正确行为）；**生成遗漏为 0**——lite 模型会逐字保留上下文中的关键词写法。
- **决策**：按 design 既定原则「修订 expected_keywords 而非放宽目标值」，将 16 条旧样本关键词修订为文档原文逐字形式（如「24 小时」）；prompt 模板与上下文组装策略本轮**不改**（主导失效类别不是生成/组装）。Q013 为推理型样本（答案「7 个工作日」是计算结果，不在原文），其检索层覆盖率口径豁免，仅以答案层判定。
- **放弃**：直接调 prompt 提指标（无法区分失效环节，且实测生成环节无遗漏）；关键词匹配做空格/同义词归一化（会掩盖真漏答，保持机械口径可回归）。
- **改判条件**：bge-m3 全量回归（≥100 条）后若生成遗漏占比显著上升，再评估 prompt/组装策略调整。
- **备注**：本轮归因与首轮全量回归（122 条）用 bge-small-zh-v1.5 替代嵌入完成（bge-m3/bge-reranker 下载受网络限制，huggingface.co 不可达、镜像 ~0.1-0.5MB/s 反复断流）。全量回归结果：检索 Top-5 98.26%、答案层覆盖率 **91.74%（≥0.85 达标）**、对抗样本 5/7；失效模式 retrieval_miss=2 / assembly_omission=2 / generation_omission=12——抽查 12 条生成遗漏多为同义转述与中英间空格差异（如「无需提供发票」vs 关键词「不需发票」），非真漏答；2 条检索未命中（Q121/Q137）为小模型嵌入召回弱点，bge-m3 就位后须重跑确认（命令见 `enterprise-agent/eval/results/README.md`）。

## 14. 密钥管理：环境变量 + 轮换规程 + 防泄漏扫描，Vault 暂缓引入（2026-08-05，change security-hardening-plus）

- **背景**：密钥此前仅靠环境变量管理，无清单、无轮换规程、无泄漏应急与防泄漏扫描；按真实企业上线评审要求补齐「密钥全生命周期管理」能力。
- **决策**：维持「密钥只从环境变量读取」的工程约定，补齐运营闭环——密钥清单 + 轮换周期/步骤/验证 + 泄漏应急处置流程落入 `docs/30-guides/运维维护手册.md` 第 9 节；防泄漏采用 pre-commit（gitleaks，`.pre-commit-config.yaml` + `.gitleaks.toml` 豁免文档示例串）+ CI gitleaks 兜底 step 双保险；依赖与镜像漏洞扫描用 pip-audit + Trivy，High/Critical 阻断，豁免走 `deploy/security-exemptions.txt`（带复评日期）。HashiCorp Vault 等在线密钥管理服务**暂缓引入**。
- **放弃**：直接引入 Vault——单机 Docker Compose 架构下，Vault 自身成为一个需要 HA 与运维的关键依赖，成本远超收益；评审要求的「轮换、应急、防泄漏」能力由规程 + 扫描即可覆盖。Dependabot 替代 pip-audit 亦不采纳（只做 PR 提醒、不阻断流水线，不满足高危阻断门槛，可作为后续增强）。
- **改判条件**：架构演进为多机/K8s、密钥数量或轮换频率显著上升、出现合规审计硬性要求时，复评 Vault/云厂商密钥管理服务的引入。

## 15. 工单联调选型临时 stub；外部系统幂等键能力结论（2026-08-06，change ticket-system-integration）

- **背景**：真实工单系统未采购到位（自研/Jira/Zendesk 选型未定），但阶段二排期最不确定，需要提前锁定接入契约与验收用例集。
- **决策**：联调环境采用本地临时 stub（`enterprise-agent/eval/ticket_stub_server.py`，FastAPI 实现 POST/PATCH 契约 + `Idempotency-Key` 去重 + title 标记故障注入），验收用例集 7/7 通过并记录于 `openspec/changes/ticket-system-integration/acceptance.md`；真实系统到位后**必须重跑全量用例**。**幂等键能力结论**：stub 支持 `Idempotency-Key`（同键重复提交返回首次结果、至多一张工单，验收用例 2 实测）；真实系统的幂等键能力**待验证**——联调时优先确认，若不支持则按 design Risks 降级为「重试前查询是否已建单」。
- **放弃**：等真实工单系统采购到位再联调（阶段二工作量与不确定性最大，契约延后锁定风险更高）；本 change 自建 stub 产品化（临时方案，不进生产路径）。
- **改判条件**：真实工单系统选型确定并部署联调实例后，以真实实例重跑 acceptance.md 全量用例，字段命名/错误码体系/幂等键能力的契约偏差结论追加回本文件。
- **备注**：本轮验收环境为「stub + 工具层 harness」（Docker 守护进程不可用，全栈 E2E 未跑）；worker 退避重试与审计 DB 回写路径由单元测试覆盖。验收期间修复审计本地缓存文件名同秒覆盖缺陷（`AuditLogger._write_local_cache` 改纳秒时间戳）。
