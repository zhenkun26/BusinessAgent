### 2. 详细审核意见

#### 1. 项目经理 PM

- **主要问题**：C01–C25 多数已具离线实现、父项仍 open；这不是项目失败，但若继续新增能力会让作品集主线被验收矩阵淹没。F2-10/F2-11 是补证据与收敛范围任务，不是部署授权。证据：[ROADMAP](ROADMAP.md)、[交付状态](../50-engineering/delivery-status.md)。
- **改进建议**：固定一个知识问答和一个“审批后执行”的展示故事，每个故事列前提、输入、预期状态、失败例及实际证据级别；F3 逐项确认，修复与运行补证据分轨，不能把所有 BLOCKED 改成“不适用”。
- **做得好的地方**：ISSUES、OpenSpec 与交付状态区分历史、当前源码和运行验收；C10-R1/R2 有先计划、反例、回归与本地提交证据，适合说明工程决策能力。

#### 2. 软件架构师

- **主要问题**：F2-03。`check_plan` 只检查依赖关系，dispatcher 对全部子任务 fan-out，未见项目级任务数/总并发预算；SSE producer 和 consumer 之间是无容量限制的 Queue。模型输出长度、SDK 超时与重规划两轮提供局部限制，但不等于整次请求的资源预算。证据：[plan_policy.py L20](../../enterprise-agent/app/graph/plan_policy.py#L20)、[dispatcher.py L60](../../enterprise-agent/app/graph/dispatcher.py#L60)、[chat.py L305](../../enterprise-agent/app/api/chat.py#L305)。
- **改进建议**：按任务数、并发、累计调用/上下文、截止时间与队列字节数分层设限；过限在 fan-out/收费调用前明确拒绝，保留取消与不确定写入语义。避免为了 SOLID 拆出更多抽象；先将限流身份和执行预算这些真实边界集中起来。
- **做得好的地方**：每次运行独立 checkpoint 线程、精确发布指针及数据库所有权事务让原始写入与会话可见性解耦；工具 gateway、队列和 Saga 各有独立契约。源码证明设计意图，实际 PostgreSQL 锁与租约行为仍须验证。[checkpoint_access.py](../../enterprise-agent/app/graph/checkpoint_access.py)、[session_fencing.py](../../enterprise-agent/app/core/session_fencing.py)。

#### 3. QA 工程师

- **严重问题**：F2-01 在已有全量测试通过后仍可复现；现有限流测试覆盖初始化/降级/429，但没有覆盖伪造 Bearer 对限流键的影响。测试数量不能代替风险覆盖矩阵。[test_rate_limit.py](../../enterprise-agent/tests/test_rate_limit.py)、下方复现记录。
- **改进建议**：先补最小反例，再实现修复；增加真实序列化、真实请求栈与存储契约测试层，保留双进程、故障注入、取消和未知写入结果用例。当前无环境时只完善夹具和运行步骤，不能把这些项记为 PASS。CI 的镜像检查证明打包，不证明应用启动后的链路。[CI](../../.github/workflows/ci.yml)。
- **做得好的地方**：候选匹配此前 **925 tests + 249 subtests、零跳过** 的源码哈希；C10 新增 25 项含实际 Redis serializer 往返，且首轮失败没有被跳过。本轮仅核对了该证据，未重跑完整套件。[C10 记录](阶段性总结_C10检查点持久化与故障语义.md#c10-r1r2-follow-up--2026-10-19)。

#### 4. 产品经理

- **主要问题**：F2-10/F2-11。首次体验需要基础设施、模型凭证、显式迁移、创建身份、发布知识以及 API/worker；当前候选没有“新使用者从 clone 到有效回答”的实测记录。不能把配置步骤视为首次使用成功。[README 快速开始](../../README.md#快速开始)。

- **做得好的地方**：README 披露 Mock provider 和参考环境，UI 标记合成示例、未知执行状态和身份核验；无需为展示引入真实客户流程。[browser-delivery.md](../50-engineering/browser-delivery.md)、[approval-execution.md](../50-engineering/approval-execution.md)。

#### 5. DevOps 工程师

- **主要问题**：F2-04。生产 requirements 虽锁版本，镜像随后执行 `pip install --upgrade 'msgpack>=1.2.1' 'setuptools>=78.1.1'`，基础镜像也采用浮动 `python:3.13-slim`。同一源码和锁文件并不能唯一确定构建结果；这不是断言当前镜像有漏洞。[Dockerfile.prod L16–38](../../enterprise-agent/Dockerfile.prod#L16)。
- **改进建议**：选定并记录受支持的精确版本/摘要，把安全升级纳入受审阅锁定输入，核对镜像实际安装清单；维护定期更新流程，不以永久冻结绕过漏洞修复。补 SBOM/产物身份及来源策略；是否签名由实际分发渠道决定，不把缺少签名自动当成漏洞。
- **做得好的地方**：非 root、libpq/RS256 导入探针、checksum 迁移和冷备/新卷恢复流程已存在。D01–D16、O01–O16 尚未运行，恢复目标和告警有效性不能由流程文档直接验收。[retained-recovery.md](../50-engineering/retained-recovery.md)、[runtime-observability.md](../50-engineering/runtime-observability.md)。

#### 6. 安全与隐私工程师

- **严重问题**：F2-01，P1。中间件使用 `verify_signature=False` 的 `sub` 选择限流键；同一来源发送十一个不同伪造 sub 均到达下游，而不带 Bearer 时第十一个请求为 429。十次伪造同一目标 sub 后，该键的下次请求在下游执行前被 429 拒绝。攻击者无需合法 JWT 即可影响防滥用边界；业务 JWT 验证是否通过是另一个边界。[rate_limit.py L201–213](../../enterprise-agent/app/middleware/rate_limit.py#L201)、[L241–257](../../enterprise-agent/app/middleware/rate_limit.py#L241)。
- **改进建议**：优先修限流信任来源（F2-01），随后明确 Redis 故障时的共享限流策略（F2-02）。私人数据接入前还需处理 F2-05：凭证脱敏不是任意个人信息/商业文本分类，查询会写日志，检索片段会发给外部 reranker/LLM；本轮未看到真实数据泄漏，不作违规结论。[redaction.py L1](../../enterprise-agent/app/security/redaction.py#L1)、[planner.py L72](../../enterprise-agent/app/graph/planner.py#L72)、[reranker.py L50](../../enterprise-agent/app/rag/reranker.py#L50)。
- **做得好的地方**：工具 ACTION 即使遇到 skip_rbac 也检查权限，参数 schema、幂等身份和 HTTP 单次变更/保守补偿是独立于 Prompt 的控制；传输有超时、body 上限和禁止重定向。[tools/base.py L186](../../enterprise-agent/app/tools/base.py#L186)、[http_adapter.py](../../enterprise-agent/app/tools/http_adapter.py)。

#### 7. 交互与辅助功能 A11y

- **主要问题**：F2-07。账号选择/其他账号入口用 click-only div，导航为没有 href 的 a，退出为 span；这些控件缺少原生键盘可达语义。输入依赖 placeholder，聊天区没有持续内容播报语义。[index.html L270–315](../../enterprise-agent/app/static/index.html#L270)、[L328](../../enterprise-agent/app/static/index.html#L328)、[L390](../../enterprise-agent/app/static/index.html#L390)。这是源码观察，不是读屏实测结果。
- **改进建议**：用原生按钮/链接、关联 label、焦点恢复和适度 live region；先覆盖键盘登录→发问→取消→审批，再做读屏、200% 缩放和对比度验收。不要每个 SSE token 都播报；同时验证输入法组合输入下 Enter 不误发。B01–B16 不自动等于 A11y 验收。
- **做得好的地方**：部分身份和视图已有 status/alert，异步 busy 状态明确且令牌保存在内存；可在现有页面上改进，无需重写前端框架。[index.html L254](../../enterprise-agent/app/static/index.html#L254)、[browser-delivery.md](../50-engineering/browser-delivery.md)。

#### 8. 开源许可与数据合规

- **主要问题**：F2-09，证据缺口。根目录 MIT 和三个浏览器组件的许可/哈希可追溯，但没有看到覆盖整个生产依赖集合、模型服务/可选本地模型及样例语料的统一分发与来源清单。C17 manifest 证明文件身份，不证明每份数据的来源授权。本轮没有确认许可证冲突或侵权。[LICENSE](../../LICENSE)、[vendor manifest](../../enterprise-agent/app/static/vendor/manifest.json)、[RAG manifest](../../enterprise-agent/eval/rag_quality_manifest.json)。
- **改进建议**：逐项记录版本、来源、许可证、是否分发、所需声明及验证证据；作者确认样例为自写/合成还是引用，不代填归属。依据实际许可决定 NOTICE/版权保留要求，而非机械要求所有包都新增 NOTICE。外部 API 条款、数据留存和地域需在采用时另行核验。
- **做得好的地方**：已有许可证文件和浏览器资产哈希是有效基础。GitHub 的许可证识别本身并不是项目全部依赖和数据的权利审核；本轮只核对了其公开说明，不作法律认证。[GitHub 官方许可说明](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/licensing-a-repository)（查阅：2026-10-19）。

#### 9. 性能工程师

- **主要问题**：F2-03。无容量上限的 SSE Queue 使慢消费者不能向 producer 施加应用层背压；同会话租约也不限制一个用户开多个会话。模型局部输出限额仍存在，因此这里只确认“缺少明确资源门槛”，没有测得内存耗尽或无限生成。[chat.py L305–319](../../enterprise-agent/app/api/chat.py#L305)、[L399–409](../../enterprise-agent/app/api/chat.py#L399)。
- **改进建议**：设计有界队列及关闭/取消协议，特别测试队列已满时发送终态和 sentinel 不能挂住；再核对并发准入、预算耗尽及慢客户端。CPU/RSS、p95/p99、首 token 与完整响应、队列等待和失败费用分开采集。L01–L16 未测，不提供吞吐或硬件容量结论。
- **做得好的地方**：C23 保留失败/丢弃请求分母，区分 censored 时延及未观测的 worker 时延，未拿 HTTP 耗时冒充业务执行时间。[capacity-evidence.md](../50-engineering/capacity-evidence.md)。资源预算方向也与 [OWASP LLM10](https://genai.owasp.org/llmrisk/llm102025-unbounded-consumption/) 对队列、调用和配额的建议一致（查阅：2026-10-19）；OWASP 不是本项目漏洞的复现证据。

#### 11. AI Agent 保障

- **主要问题**：F2-03/F2-06。历史最多五轮、助手文本截断 200 字以及远程 embedding/rerank 的字节限制是局部保护；最终 Prompt 直接拼接历史/检索内容，未见统一的模型上下文与累计调用预算。自评 Prompt 只拿问题和回答，没有检索片段，不能独立证明答案有据可依。[history.py L168](../../enterprise-agent/app/graph/history.py#L168)、[knowledge.py L263–308](../../enterprise-agent/app/agents/knowledge.py#L263)、[defaults.py L90–100](../../enterprise-agent/app/prompts/defaults.py#L90)。
- **改进建议**：在输入过长时确定性裁剪/拒绝并保留引用映射；把检索内容作为不可信数据，增加文档注入、反事实、无答案和引用不支持的评测。语义审核与机械引用编号检查分离；不把自评分当作正确概率。F2-06 对应 C17 现有未完成验收，不另造“已通过”的新门槛。
- **做得好的地方**：工具权限、审批、幂等和 Saga 不仅靠模型遵守指令；C17 固定 122 主样本及独立角色控制，显式区分机械覆盖和人工语义判定。C10-R1/R2 结构回归仍通过既有证据，但它们不证明引用内容真实。[rag-quality.md](../50-engineering/rag-quality.md)。

#### 12. 商业可行性与客户运营

- **主要问题**：F2-11 为假设/证据缺口，无实际客户、付费意愿、替代流程成本、支持工时或部署故障数据。样例产品手册里的价格属于测试语料，不是 BusinessAgent 的报价。商业评分 PENDING，也不因此否定求职作品价值。[样例产品手册](../../enterprise-agent/eval/sample_docs/产品手册.md)、[交付边界](../50-engineering/engineering-delivery-baseline.md)。
- **改进建议**：优先验证“有权限的政策问答”和“审批后创建工单”两类假设场景，与普通搜索/表单加规则流比较，衡量完成率、人工纠错、每个成功任务成本。若将来考虑试点，先补需求访谈和运营负责人，再决定产品化；当前不创建商业化排期。
- **做得好的地方**：Mock、受控 HTTP 和真实企业接入被分开，HTTP 补偿及审计契约可作为集成成本讨论的具体材料；项目已主动披露没有企业落地，可据此形成可信求职叙事。

### 3. 关键风险与行动建议 (Top 3)

1. **先修限流身份信任（F2-01 / C05、C09、C24，P1）**。下一次授权只推进这个增量：未验证 JWT 不得决定用户额度；匿名/IP 门槛独立保留，已验证用户额度不能被伪造请求消费。验收包含同源轮换 sub、冒充目标 sub、坏签名/过期/错误类型/超长 sub、合法用户隔离及 429 回归。不得以业务最终返回 401 作为限流正确的证明。
2. **补齐执行资源边界（F2-03 / C08、C23，P2）**。拆成子任务/上下文预算和 SSE 背压两个有界增量，不一次大改。验收先以 deterministic doubles 证明过限不发起额外收费调用、队列满时可取消/退出、终态不重复，再将慢客户端与多用户运行留在隔离环境。没有真实容量数据前不承诺 QPS、p95 或成本上限。
