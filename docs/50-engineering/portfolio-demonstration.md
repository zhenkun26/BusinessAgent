## Reusable bounded-review workflow

Use this workflow for a later interview section, speech segment, README claim, screenshot
set or engineering explanation. This is a reusable procedure, not authorization to process
the whole repository or upload its contents. Start with one specifically confirmed unit.

| Step | Work and minimum input | Reviewable output / exit condition |
| --- | --- | --- |
| 1. Bound the unit | Identify audience, purpose, one target material and the current authorization. Read project rules and existing local changes. | Written scope/non-goals, allowed changes, execution and upload boundaries. Preserve unrelated work. |
| 2. Freeze the baseline | Record Git revision, relevant versions and target-file hashes. Read only the necessary local excerpts and authoritative contracts. | Evidence has a reproducible identity; historical and current material are distinguishable. |
| 3. Extract claims | List concrete assertions: implemented behavior, observed results, desired outcome, comparison or commercial hypothesis. | Each claim has a source, evidence level, date/revision and missing-evidence note. Unsupported claims stay explicitly unsupported. |
| 4. Plan the smallest change | Choose whether to retain, qualify, replace or defer each claim. Identify data/asset provenance and any side effects. | Plan and acceptance precede edits. Do not open a new dependency, runtime or business-validation workstream implicitly. |
| 5. Implement one artifact | Write source-traceable wording, a short narrative and concrete failure/limitation examples. Label Mock and planned outputs. | Candidate artifact is reviewable without private data or invented results; unresolved facts remain pending. |
| 6. Verify at the right level | Check links, source facts, version/hash consistency and stated limits. Run relevant existing checks for changed behavior or inventory. | Record checks actually run; separate static review, retained results, fresh tests and unavailable live checks. A prose change does not automatically require the full suite. |
| 7. Review disclosure and exposure | Read as an external reviewer: can a reader mistake a target for a measurement, a Mock for a real provider, or old CI for current acceptance? | Correct misleading wording. Verify the exact content proposed for any later sharing; no whole-repository upload by default. |
| 8. Record and hand off | Update the actual status ledger and applicable OpenSpec artifacts; review diff; commit locally if authorized. | Report commit, scope, verification and blockers. Stop at the agreed gate. Push, sharing, runtime execution and next-unit work require their own applicable authorization. |

### Minimal exposure rules

- Prefer local source inspection and local checks. An external reviewer or connector is
  not required to make the evidence matrix useful.
- If sharing is separately requested, first identify the destination, recipient, purpose
  and exact files/excerpts needed. Share only that agreed subset; no implied permission
  to upload the repository, ignored evidence directory, old deck or sample corpus.
- Exclude credentials, personal/customer data and unrelated code. Use placeholders or
  source references when raw content is unnecessary. Do not treat redaction as permission
  to distribute an asset with unresolved rights.
- Record what was shared and what was withheld. A local commit is not an upload; a link
  to a local ignored receipt is not portable evidence. Missing evidence is a reason to
  qualify a claim, not to fabricate a transcript.
