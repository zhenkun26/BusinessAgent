## 1. 服务组成与启动顺序

```
启动顺序(依赖自下而上):
  ① Docker 基础设施(必启):etcd / minio / milvus-standalone / postgres / redis
  ② API 服务(依赖 ① 全 healthy)
  ③ Worker 服务(后台任务:审批超时扫描/文档入库队列/Saga 补偿重试/审计回写;可选但推荐)
  ③ 监控(可选):prometheus / grafana / jaeger
```

**启动(每次开机/重启后)**:

> **一键方式(推荐,2026-07-28 新增)**:双击项目根目录 `启动智多星.bat`——自动检查并补齐
> Docker 引擎(未运行则拉起 Docker Desktop 并等待)、5 个基础设施容器(缺失才 compose up)、
> API(健康检查不过则后台拉起 uvicorn 并轮询到 healthy),全部就绪后自动用 Chrome 打开
> `http://localhost:8000/ui`。幂等,环境已就绪时双击等于纯检查 + 开网页。
> 注意:bat 内写死了本机三处路径——conda python(`D:\ProgramData\anaconda3\envs\enterprise_agent`)、
> Chrome(`C:\Users\Lenovo\AppData\Local\Google\Chrome\Application`)、Docker Desktop(`C:\Program Files\Docker\Docker`),换机器需改;API 日志在最小化的「智多星-API」窗口。
> 下面的手动方式仍适用于排错和监控组件启动。

```bash
cd /d/Project/企业agent/enterprise-agent

# ① 基础设施(约 30-60s 变 healthy)

docker ps --format "{{.Names}} {{.Status}}"     # 确认 5 个 (healthy)

# ② API(Git Bash 窗口 A,前台跑着别关)
PYTHONIOENCODING=utf-8 /d/ProgramData/anaconda3/envs/enterprise_agent/python.exe \
  -m uvicorn app.main:app --host 127.0.0.1 --port 8000

# ③ Worker(另开窗口;审批超时扫描 60s/次 + 队列消费 + 审计回写)
PYTHONIOENCODING=utf-8 /d/ProgramData/anaconda3/envs/enterprise_agent/python.exe -m app.worker
# 启动日志应看到:DB 连接池就绪 → Milvus 已就绪 → 工具注册 7 个 → Prompt 缓存已刷新(11 个名称)

# ③ 监控(可选)
```

## 2. 本机环境特殊性(踩过的坑,别再踩)

| 事项 | 说明 |
|------|------|
| Python 解释器 | conda 不在 PATH,用绝对路径 `/d/ProgramData/anaconda3/envs/enterprise_agent/python.exe`(env 名 `enterprise_agent`,Python 3.11.15) |
| 终端 | 一切命令在 **Git Bash** 执行;PowerShell 不支持 `<` 重定向/`VAR=值` 前缀/heredoc |
| 中文乱码 | 命令前加 `PYTHONIOENCODING=utf-8`;curl 中文 body 必须 `--data-binary @文件`,不能 `-d` 直接写 |
| 端口残留 | 重启 API 前先查:`netstat -ano \| grep :8000` \| 有残留则 `taskkill //PID <pid> //F` |
| uvicorn reload | Windows 上不可靠(卡死),所以启动命令不带 --reload;改代码后手动重启 |
| Docker 依赖 | API 起不来先查 `docker ps`——Docker 没启是最常见原因(PG 连接拒绝) |
| 模型路径 | bge-m3 / bge-reranker-large 在 `D:/models/`;首次调用有冷加载(首请求 +30-60s) |

## 3. 常见维护操作

### 3.0 外部系统提供方切换（当前仅允许测试环境）

CRM、邮件和工单支持逐系统 provider 开关；逐系统变量为空时继承全局 `TOOL_PROVIDER`。默认值必须保持 `mock`：

```dotenv
TOOL_PROVIDER=mock
CRM_TOOL_PROVIDER=
MAIL_TOOL_PROVIDER=
TICKET_TOOL_PROVIDER=
```

真实系统契约、沙箱和凭证确认前，不得把 `CRM_TOOL_PROVIDER` 或 `MAIL_TOOL_PROVIDER` 切为 `http`。测试环境切换后先执行对应契约测试，并核对审计中的 `provider` 字段；回退时将对应变量清空或设回 `mock`，重启 API 后复核 `/ready` 与工具审计。SSO 配置当前保持 `SSO_ENABLED=false`，IdP 端点和声明字段确认后再单独实施。

### 3.1 知识库:入库新文档

```bash
PY=/d/ProgramData/anaconda3/envs/enterprise_agent/python.exe

# 公司共享文档(所有人可见)
$PY -m app.rag.ingest <文件或目录> --type policy --ns shared_company

# 部门专属文档(必须显式指定角色,否则默认全角色可见!)
$PY -m app.rag.ingest <文件> --type policy --ns dept_sales --roles salesperson manager admin
```

- 分区可选:`dept_sales / dept_finance / dept_cs / dept_hr / shared_company / restricted_exec`
- `--type`:`policy / product / faq / manual`
- **入库是增量追加,日常加文档直接跑 CLI 即可,不要 recreate Collection**——全量重建(init_milvus(recreate=True) + run_w9_milvus)仅用于开发期推倒重来,且会清掉 dept 分区文档需逐个补入
- 传错分区名会静默落入 shared_company(有 warning 日志),注意看输出
- 验证:`docker compose exec -T postgres psql -U agent enterprise_agent -c "SELECT count(*) FROM …"` 或前端直接提问测

### 3.2 用户管理(成员加入/变更/离职)

> 原则:**日常变更一律增量 SQL,不要清库重建**——DROP SCHEMA 会把 sessions/audit_logs/approval_requests 一起抹掉,仅用于开发期整体重置。init.sql 底部的种子区只对**新库**生效;改现库直接 SQL,两者互补(新成员最好两边都加)。
>
> **2026-08-04 起优先使用用户管理 API**(admin 角色):`GET/POST /admin/users`、
> `PATCH /admin/users/{id}`(角色/部门/禁用),密码自动 bcrypt 哈希、变更自动审计;
> 重复用户名返回 409。API 与 SQL 二选一,不要混用同一字段的并发修改。

```bash
# 创建用户(API)
curl -s -X POST http://127.0.0.1:8000/api/v1/admin/users \
  -H "Authorization: Bearer $TOKEN_ADMIN" -H "Content-Type: application/json" \
  -d '{"username":"新同事赵六","role":"salesperson","department":"dept_sales","initial_password":"ChangeMe123!"}'

# 禁用/改角色(API,即时生效)
curl -s -X PATCH http://127.0.0.1:8000/api/v1/admin/users/<user_id> \
  -H "Authorization: Bearer $TOKEN_ADMIN" -H "Content-Type: application/json" \
  -d '{"is_active":false,"role":"manager"}'
```

> 认证加固:登录密码校验由 `AUTH_REQUIRE_PASSWORD` 开关控制(演示默认关=密码任意,
> 生产开=bcrypt 校验 + 统一 401);`get_current_user` 回查 users 表
(`AUTH_CHECK_DB`,默认开),禁用用户旧 token 立即失效。

**新成员加入**(无需动 init.sql、无需重启):

```bash
docker compose exec -T postgres psql -U agent enterprise_agent -c "
INSERT INTO users (user_id, username, email, role, department)
VALUES ('user_sales_004', '新同事赵六', 'zhaoliu@company.com', 'salesperson', 'dept_sales')
ON CONFLICT (user_id) DO NOTHING;"
```

- `role` 必须是 5 角色之一:salesperson / customer_service / finance / manager / admin
- `department` 必须是分区命名空间:dept_sales / dept_finance / dept_cs / dept_hr / shared_company
- 这两个字段直接决定可用工具(RBAC)和可见文档(命名空间),填错=权限错
- 登录用 `username`(开发期不校验密码)

**改角色/部门/离职**:

```bash
PSQL="docker compose exec -T postgres psql -U agent enterprise_agent"

# 升职改角色
$PSQL -c "UPDATE users SET role='manager' WHERE username='销售员张三';"
# 调部门(角色通常要一起改)
$PSQL -c "UPDATE users SET department='dept_finance', role='finance' WHERE username='销售员张三';"
# 离职(软删除,保留审计追溯)
$PSQL -c "UPDATE users SET is_active=false WHERE username='销售员张三';"
```

**生效时机**:JWT 里携带 role/department,已签发的 token 在过期前仍是旧权限——改完让本人重新登录(或等 token 过期)才生效。JWT 过期时间见 `.env` 的 `JWT_ACCESS_TOKEN_EXPIRE_MINUTES`。

**PowerShell 导入 SQL 文件时**:先 `$OutputEncoding = [System.Text.Encoding]::UTF8` 再 `Get-Content -Encoding UTF8 | docker exec -i … psql`(否则中文种子变 `?????`;判断数据是否真坏用 `SELECT username, octet_length(username) FROM users`,中文应 = 字数×3)。

**用户管理 API**:已补齐 admin 专用用户管理端点(`GET/POST /admin/users`、`PATCH /admin/users/{id}`,2026-08-04),成员变更优先走 API,SQL 仅作兜底。

## 5. 故障排查

| 现象 | 处理 |
|------|------|
| API 起不来,报 ConnectionRefused | `docker ps` 查基础设施;没启先 `docker compose up -d …` |
| API 起不来,端口被占 | `netstat -ano \| grep :8000`,`taskkill //PID <pid> //F` |
| 前端 /ui 空白 | F12 看 Console;CDN(vue/marked)需要联网;Ctrl+F5 强刷 |
| 前端 sources 显示 0.000/空标题 | 该 bug 已于 2026-07-26 修复(LangChain 序列化 kwargs 未解包,详见第 8 节);确认 API 已重启加载新代码 |
| 审批批准后状态卡在 approved_pending_reauth | 种子审批单缺 requester_token(2026-07-27 已修,见第 8 节);跑 `scripts/fix_seed_approvals.py` 补 token;动态建单出现此状态则是发起人 token 真过期,需其重新登录后 resume |
| 审批显示 executed 但工具执行失败 | 2026-07-27 起审批结果直接显示失败原因(message 字段);常见原因:发起人角色与工具不匹配(RBAC,如 salesperson 用 create_ticket) |
| 前端改了不生效 | index.html 是静态文件无需重启 API,但浏览器有缓存,Ctrl+F5 强刷 |
| 知识问答"未覆盖"但文档在 | 置信度兜底(拒答优于编造);用 `eval/run_p2_namespace.py` 验证检索;已知一例召回排序问题(P3 待办) |
| Milvus 检索返回 0 条 | 查 collection 实体数:`/ready` 的 `milvus.num_entities`;0 则需重新入库(手册 0.2) |
| checkpointer 显示"未初始化" | 正常,首次对话后惰性初始化;应为 redis,降级则查 RediSearch 模块 |
| 首次请求特别慢(100s+) | 模型冷加载,第二次起正常 |
| audit_logs 无新记录 | PG 是否 healthy;审计降级时会写 `logs/audit/` 本地文件 |

## 9. 密钥管理与泄漏应急（security-hardening-plus，2026-08-05）

### 9.1 密钥清单

| 密钥/凭证 | 存放位置（环境变量） | 用途 | 轮换周期 | 验证方式 |
|---|---|---|---|---|
| JWT 签名密钥 | `JWT_SECRET_KEY` | 签发/校验用户 token | 90 天 | 重启后旧 token 应 401；新登录签发的 token 可访问 `/health` 受保护接口 |
| PostgreSQL 口令 | `POSTGRES_PASSWORD` | 业务库/审计/sessions | 90 天 | `docker compose exec postgres psql -U agent -d enterprise_agent -c 'select 1'` |
| Redis 密码 | `REDIS_PASSWORD`（与 compose `requirepass` 一致） | checkpointer/限流/队列 | 90 天 | `redis-cli -a <新密码> ping` 返回 PONG；`/ready` redis healthy |
| Milvus 口令 | `MILVUS_PASSWORD` | 向量库访问 | 90 天 | `/ready` milvus healthy |
| DeepSeek API Key | `OPENAI_API_KEY` | 云端 LLM（primary/lite） | 180 天或按供应商要求 | `curl -H "Authorization: Bearer <key>" https://api.deepseek.com/v1/models` 返回 200 |
| 外部业务系统 token | `CRM_API_TOKEN` / `MAIL_API_TOKEN` / `TICKET_API_TOKEN` | http 工具适配器 | 随对方系统策略 | `TOOL_PROVIDER=http` 冒烟调用返回非 401 |
| GHCR token | CI `GITHUB_TOKEN`（自动注入） | 镜像推送 | 由 GitHub 托管（PAT 场景 90 天） | CI docker job 登录并推送成功 |
| Cohere Key（可选） | `COHERE_API_KEY` | 云端 reranker | 180 天 | reranker 冒烟调用返回 200 |

> 原则：密钥只从环境变量读取，`.env`/`.env.local`/`.env.prod` 永不提交（`.gitignore` 已覆盖，
> pre-commit + CI gitleaks 双保险拦截）。代码内仅保留开发默认占位值，
> 生产启动时 `validate_production_settings` 会拦截默认凭证上线。

### 9.2 轮换步骤（通用流程）

1. **生成新值**：`openssl rand -base64 32`（JWT/PG/Redis 等自管密钥）；云厂商密钥在控制台重新签发。
2. **更新环境**：改 `.env.prod`（或部署平台的密钥配置）；PG/Redis/Milvus 需同步改服务端口令
   （PG：`ALTER USER agent WITH PASSWORD '...'`；Redis：改 compose `requirepass` 并重建容器）。
3. **滚动重启**：`docker compose up -d redis postgres`（口令类）→ 重启 API 与 worker 进程。
4. **验证**：按 9.1 表「验证方式」逐项确认；JWT 轮换后通知在线用户重新登录（旧 token 立即失效）。
5. **记录**：在 ISSUES.md/CHANGELOG 记录轮换日期与操作人（不记密钥本身）。

### 9.3 密钥泄漏应急处置

发现任一密钥疑似泄漏（gitleaks 命中、日志外泄、误提交、第三方告警）时：

1. **吊销/轮换（30 分钟内）**：云厂商密钥立即在控制台吊销并换新；自管密钥按 9.2 立即轮换。
2. **影响面核查**：
   - 查 git 历史确认泄漏范围（`docker run --rm -v "$PWD:/repo" zricethezav/gitleaks git /repo`）；
   - 若密钥已进历史：轮换即失效优先；必要时 `git filter-repo` 清理历史并强推（先与责任人确认）；
   - 查审计日志（`audit_logs` 表）确认泄漏窗口内是否有异常调用。
3. **审计记录**：事件、影响面、处置动作、时间线写入 ISSUES.md（安全事件条目），
   复盘是否需调整 allowlist 或规程。

### 9.4 防泄漏扫描与误报处置

- **pre-commit**：仓库根 `.pre-commit-config.yaml`（gitleaks v8），`pre-commit install` 后提交即扫；
  全量自查：`pre-commit run --all-files`。
- **CI 兜底**：`.github/workflows/ci.yml` test job 的 gitleaks step 扫 git 历史，命中即失败。
- **allowlist 维护**：`.gitleaks.toml`（继承默认规则集 + 项目豁免：文档示例串、测试桩值、
  开发默认占位）。误报处置：确认为假密钥/示例串后，往 `[allowlist].regexes` 加精确串
  或往 `paths` 加路径，并注明原因——禁止整目录豁免源码。
- **验证**：把含 `sk-<高熵串>` 的临时文件放进仓库跑一次扫描，应检出 1 条（本规程已实测）。

### 9.5 漏洞扫描豁免清单

依赖/镜像漏洞的豁免条目统一维护在 `enterprise-agent/deploy/security-exemptions.txt`
（`<VULN-ID> | <复评日期> | <理由>`）：仅 Medium 及以下可豁免，High/Critical 必须修复；
复评日期到期前必须复评。CI 中该文件被解析为 pip-audit `--ignore-vuln` 与 Trivy `.trivyignore`。

## 10. 值班预案（load-test-and-dr-drill，2026-08-05）

> 与告警规则 `enterprise-agent/deploy/prometheus-alerts.yml` 逐项对应；规则变更时本节同步评审。
> 通知通道（Alertmanager/邮件/webhook）尚未落地，当前以 Grafana :3000 与 Prometheus 告警页
> 人工巡检为观察入口——值班期间每 30 分钟查看一次告警列表。

### 10.1 告警分级

| 级别 | 定义 | 对应 severity | 响应时限 |
|---|---|---|---|
| 紧急 | 服务不可用 / 关键依赖异常 / 资源临近耗尽，需立即处置 | critical | 15 分钟内介入 |
| 重要 | SLA 承诺线被突破的趋势信号，未必然影响用户 | warning | 当日处理，连续 24h 不收敛则升级紧急 |
| 提示 | 巡检、报告类信息（当前无此类规则） | info | 周会 review |

### 10.2 告警响应动作（与规则文件逐项对应）

**紧急（critical，运维口径）**

| 告警 | 响应动作 | 升级路径 |
|---|---|---|
| ApiDown | ① `curl localhost:8000/health` 确认；② 查 API 进程/容器日志；③ 起不来按第 5 节「API 起不来」处置 | 15 分钟未恢复 → 通知负责人，按第 3.5 节准备从最近备份恢复 |
| ApiP95LatencyHigh（p95>5s） | ① 看 Grafana 分接口延迟定位慢接口；② 查云端 LLM 是否限流（日志 `llm_degradation`）、Milvus 内存、uvicorn worker 占用；③ 必要时重启 API 并降载 | 30 分钟不收敛 → 负责人决策限流（DEPLOY.md 7.3 nginx 限流） |
| ApiErrorRateHigh（>5%） | ① 查 `audit_logs` 与 API 日志的错误类型分布；② 区分 5xx 来源（依赖故障/代码缺陷/上游限流） | 伴随依赖告警按其预案走；30 分钟不收敛 → 负责人 |
| PostgresDown | ① 区分「PG 宕机」与「postgres-exporter 失联」（`docker ps` 看两个容器）；② PG 真宕机：`docker compose up -d postgres` 拉起并查日志 | PG 无法拉起 → 启用恢复流程（DEPLOY.md 5.3，实操修正见 10.4） |
| PostgresConnectionsHigh（>80） | ① `pg_stat_activity` 查连接来源；② 确认 API 连接池是否泄漏 | 伴随延迟告警 → 重启 API 释放连接 |
| RedisDown | ① 区分宕机与 exporter 失联；② Redis 故障时 checkpointer/限流自动降级，优先恢复 Redis | 10 分钟未恢复 → 负责人；期间关注 PG 负载（降级链压到 PG） |
| RedisMemoryHigh（>80%） | ① `redis-cli info memory` 确认；② 检查 checkpoint TTL 是否生效（ISSUES I-06）；③ 必要时提 maxmemory 或清理大键 | 持续增长 → 负责人评估扩容 |
| MilvusDown | ① `docker compose up -d milvus-standalone`；② 检索自动降级 BM25/关键词，问答质量下降但服务可用 | 无法拉起 → 负责人；恢复后验证 `/ready` milvus healthy 与实体数 |
| MilvusMemoryHigh（>3.2G） | ① 查 collection 规模与 segment 增长；② 评估升配（prod compose 内存上限 4G） | 伴随 OOM 重启 → 负责人 |
| DiskUsageHigh（>85%） | ① `docker system df` 定位；② 清理 json-file 日志与无用镜像（DEPLOY.md 7.4） | 清理后仍 >85% → 负责人决策扩盘 |
| HostMemoryHigh（>90%） | ① 确认占用大户（Milvus/API/模型）；② 停非必要容器，按 DEPLOY.md 2.1 核对配置基线 | 持续耗尽 → 负责人决策升配或拆机部署 |

**重要（warning，SLA 口径）**

| 告警 | 响应动作 |
|---|---|
| ApiP95LatencySlaBreached（p95>2s） | 记录趋势，与压测报告比对；连续出现说明容量接近 SLA 边界，安排复测（`eval/run_load_test.sh`） |
| ApiP99LatencySlaBreached（p99>5s） | 同上，重点看长尾来源（冷加载/慢 LLM 调用） |

| ApiAvailabilitySlaRisk（1h 窗口 >0.5%） | 可用性预算告急，当日必须定位原因并给出结论 |

### 10.4 备份恢复执行要点（2026-08-05 首演发现、2026-08-06 复演验证）

DEPLOY.md 5.3 已按两轮实测修正（演练记录见 ISSUES I-12），要点：

1. **PG 恢复前先清库**：目标库已有 schema 时（如 init.sql 初始化过的新实例），先
   `DROP SCHEMA public CASCADE; CREATE SCHEMA public;` 再回放 `pg_*.sql.gz`，否则建表冲突。
2. **etcd 恢复必须先停 etcd 并清空数据目录**：在运行中的 etcd 上
   `etcdctl snapshot restore --data-dir /etcd` 必失败（目录非空/被锁）。正确步骤：
   停 milvus → 停 etcd/minio → 清数据卷 → 临时容器 restore/解包 → 启 etcd/minio → 启 milvus。
   可复用演练覆盖文件 `deploy/docker-compose.dr-drill.yml` 在隔离 project 中先验证。
3. **Milvus 可恢复 = 三件套缺一不可**：etcd 元数据 + MinIO 对象（向量数据本体）+ milvus
   本地卷。`scripts/backup.sh` 自 2026-08-06 起四类产物齐全（pg/etcd/minio/milvus）；
   复演实测全栈 RTO ≈ 194 秒，集合 load 成功且 query 返回数据。
4. **一致性核查口径**：Milvus 仅看 `get_collection_stats` 不算数（读的是元数据，
   segment 缺失时数字也一致）——必须 `load_collection` 成功并跑真实 query。
