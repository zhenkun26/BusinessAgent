# 智多星 UAT 验收计划

> 状态：草案（2026-08-15）
>
> 本文用于组织真实用户验收，不代表 UAT 已完成。种子用户只能用于技术彩排，不能替代真实员工验收；stub 或 Mock 只能证明契约和治理链路，不能证明真实外部系统副作用。

## 1. 验收目标与边界

本轮 UAT 验证员工是否能够在真实业务语境下完成六类核心任务：

1. 知识问答；
2. 部门命名空间隔离；
3. 数据分析；
4. 工具执行；
5. 审批流；
6. 跨部门业务协作。

当前验收基线为 `v1.3.0` 内部落地版本，执行脚本和预期结果复用 [使用案例手册](使用案例手册.md)。CRM、邮件和工单真实系统接入以 `crm-mail-sso-integration` 与真实系统联调结果为准；在真实系统尚未接通前，UAT 只能验收工具治理、审批、审计、失败处理和 Mock/stub 契约，不得把 Mock 返回值写成真实业务结果。

### 2.3 G0 技术彩排数据

已生成一批可复现的合成数据，供真实 UAT 前先验证场景编排、权限边界、审批状态和审计采集：

- 数据文件：`enterprise-agent/eval/uat_simulation/fixture.json`
- 生成器：`enterprise-agent/eval/generate_uat_simulation.py`
- 覆盖范围：11 个模拟用户、12 个客户、24 个订单、12 个工单、8 个知识文档、6 个会话、8 个审批、12 个 UAT 场景
- 安全标记：全部使用 `SIM-`/`sim-` 前缀、`example.invalid` 或 `.internal` 测试地址，不包含密码、token 或真实客户信息
- 使用边界：`official_uat=false`、`external_side_effects_allowed=false`；不直接导入数据库，不连接 CRM、邮件、工单或生产环境

在 `enterprise-agent/` 目录执行以下命令可生成并回放 G0 数据：

```bash
python eval/generate_uat_simulation.py --check
python eval/run_uat_replay.py
```

默认报告写入 `enterprise-agent/eval/results/uat_replay_report.json` 和 `uat_replay_report.md`。回放器只做结构、权限和安全契约检查，不执行 API、数据库或外部系统动作；报告中的 `formal_uat=false`、`release_evidence=false` 必须保持不变。该数据只能把执行记录标记为“G0 技术彩排”，不能替代真实员工、真实 UAT 环境或真实外部系统返回证据。

## 3. 角色分工

| 角色 | 职责 |
|---|---|
| 验收用户 | 按业务语言执行场景，确认结果是否满足工作需要，记录体验问题 |
| 产品负责人 | 确认场景优先级和通过标准，裁决业务语义争议 |
| 研发负责人 | 提供版本、修复 P0/P1、解释技术日志，不替代业务验收 |
| 运维负责人 | 准备环境、监控指标、备份和回滚，记录运行证据 |
| 记录人 | 为每个场景保存输入、输出、时间、截图/日志、问题单和复验结论 |

## 4. UAT 场景矩阵

每个核心场景必须由真实员工执行至少一次；同一场景的种子用户执行记录只能标记为“彩排”。

| 编号 | 核心场景 | 建议角色 | 手册依据 | 最小验收动作 | 通过标准 |
|---|---|---|---|---|---|
| UAT-K01 | 共享知识问答 | 销售/客服 | §4、F4 | 查询销售政策或产品制度 | 回答有来源标注，事实与文档一致，无法覆盖时明确拒答 |
| UAT-K02 | 部门命名空间隔离 | 销售、客服、财务 | §5、F5 | 跨部门分别查询专属制度 | 有权限角色命中，无权限角色不得看到专属内容 |
| UAT-A01 | 数据对比分析 | 销售/财务 | §6、F6 | 对比 C001 与 C002 业务数据 | 数字来自真实聚合，口径和结果可解释 |
| UAT-A02 | 权限限制下的数据请求 | 客服 | §6.5、§8 | 请求无权访问的数据或工具 | 友好拒绝，不返回越权数据，不产生 500 |
| UAT-E01 | 查询业务记录 | 销售/客服 | §7.1-§7.3、F7 | 查询客户、订单或工单 | 返回字段完整，角色权限正确，结果标识数据来源 |
| UAT-E02 | 多步骤工具执行 | 客服/经理 | §7.4-§7.6、§9X | 执行查询→建工单→通知链路 | 步骤顺序、结果关联、失败处理和审计记录正确 |
| UAT-P01 | 高风险操作审批 | 销售/经理 | §9、F9 | 发起外部邮件或其他高风险动作 | 未审批不执行，审批后仍按发起人权限执行 |
| UAT-P02 | 越权审批与拒绝 | 客服/经理 | §9.3、§8 | 非审批角色尝试批准，审批人拒绝一单 | 返回正确 403/状态，所有决策可审计 |
| UAT-C01 | VIP 客户跨部门协作 | 销售/经理/客服 | §9X.1、F9X.1 | 客户跟进→审批→工单查询 | 各角色只看到授权数据，流程可追踪 |
| UAT-C02 | 退款争议协作 | 客服/财务 | §9X.2、F9X.2 | 工单、订单、退款状态联合核对 | 数据口径一致，权限和责任边界明确 |
| UAT-C03 | 紧急问题升级 | 客服/经理 | §9X.3、F9X.3 | 查询客户→工单升级→通知 | 多步骤结果关联，失败能定位和补偿 |
| UAT-O01 | 取消、恢复与反馈 | 任一角色/管理员 | §10-§12、F10-F11 | 取消长请求、续聊、点踩反馈 | 会话终态正确，审计链完整，反馈进入知识治理流程 |

## 5. 场景通过标准

单个场景只有同时满足以下条件才算通过：

- 业务预期结果逐项满足；
- 无越权、敏感数据泄漏或错误执行；
- 关键响应满足 `production-readiness` 的 SLA 口径；
- 审批、工具、失败、取消和反馈等状态可在审计或会话记录中追溯；
- 发现的问题已创建 issue，且没有未接受的 P0/P1；
- 真实外部系统场景必须有真实系统返回证据，Mock/stub 结果只能标记为技术彩排。

核心场景全部通过是 UAT 硬门槛；非核心 P2 问题可在产品负责人书面接受风险后进入灰度观察，但不得影响权限、审批、数据正确性和审计完整性。

## 7. 当前结论

- UAT 计划已具备执行结构，但真实验收用户、环境、排期和签署人尚未确认；
- I-02 保持 `open`，不得因为本文建立而关闭；
- 种子用户和自动化脚本可用于彩排，不能作为正式 UAT 证据；
- 真实系统接入完成前，外部副作用类场景只能以契约/治理验收记录为证据。
