## 一、改进项分级标准

| 优先级 | 定义 | 处理时限 |
| :-- | :-- | :-- |
| **P0** | 阻断性缺陷,导致系统不可用或核心流程断裂 | 立即修复(已全部完成) |
| **P1** | 重要功能缺陷,影响业务完整性或体验,但不阻断核心流程 | MVP 第二轮迭代内修复 |
| **P2** | 增强性建议,提升健壮性、可维护性或扩展性,非必需 | MVP 之后规划 |

## 二、P0 关键缺失(已修复)

P0 项已在 v2 方案 [第十八章 附录 B](企业知识工作流Agent产品方案_v2_LangGraph版.md#十八附录-bp0-关键缺失补充实现) 中全部补充实现。

### P0-1:fallback_node 空实现

| 项 | 内容 |
| :-- | :-- |
| **问题** | 原方案 `workflow.add_edge("fallback", END)` 无节点实现,任何失败都返回空 |
| **影响** | 任意错误导致用户无反馈,体验灾难 |
| **修复方案** | `ErrorClassifier`(12 类错误枚举 + 正则匹配)+ `FallbackExecutor`(分级兜底动作,含副作用如创建工单)+ `fallback_node` 完整实现 |
| **修复位置** | v2 方案 18.1 节 |
| **状态** | ✅ 已修复 |

### P0-2:并行执行未实现

| 项 | 内容 |
| :-- | :-- |
| **问题** | 图结构画了 KA/AA 并行,但代码用顺序条件路由,未用 LangGraph `Send` API |
| **影响** | knowledge + analysis 无法并行,响应时间翻倍 |
| **修复方案** | State 扩展 `parallel_results` reducer + `route_after_planner_parallel` 返回 `list[Send]` + `wait` 同步点 + Aggregator 改造消费并行结果 + `build_workflow_v2()` |
| **修复位置** | v2 方案 18.2 节 |
| **状态** | ✅ 已修复 |

### P0-3:LLM/Milvus/Redis 无降级链

| 项 | 内容 |
| :-- | :-- |
| **问题** | 单点故障无兜底,LLM 限流或 Milvus 不可用时整个系统瘫痪 |
| **影响** | 可用性无法达到 99% 目标 |
| **修复方案** | LLM 四级降级(主/备/本地/FAQ + 熔断器)+ Milvus 三级降级(向量/BM25/PG)+ Redis 三级降级(Redis/PG/内存) |
| **修复位置** | v2 方案 18.3 节 |
| **状态** | ✅ 已修复 |

### P0-4:Saga 回滚未实现

| 项 | 内容 |
| :-- | :-- |
| **问题** | 多次提及 Saga 模式但无代码,多步 execution 失败时已执行步骤无法回滚 |
| **影响** | 数据不一致(如任务已创建但邮件发送失败,产生孤儿任务) |
| **修复方案** | `CompensationRegistry`(工具补偿动作注册)+ `SagaCoordinator`(顺序执行+逆序补偿)+ `batch_id` 事务批次机制 |
| **修复位置** | v2 方案 18.4 节 |
| **状态** | ✅ 已修复 |

### P0-5:JWT 过期未处理

| 项 | 内容 |
| :-- | :-- |
| **问题** | 审批等待数小时后 JWT 过期,审批通过后执行 401 |
| **影响** | 长流程必定失败,审批机制形同虚设 |
| **修复方案** | `JWTManager`(过期检查/刷新)+ 审批恢复强制刷新 + `approved_pending_reauth` 状态 + `/pending-executions/{id}/resume` 重新授权 API + 工具调用前 JWT 校验 |
| **修复位置** | v2 方案 18.5 节 |
| **状态** | ✅ 已修复 |

## 三、P1 重要缺陷(待完善)

P1 项影响业务完整性,需在 MVP 第二轮迭代内修复。

### P1-1:批量审批逻辑断裂

| 项 | 内容 |
| :-- | :-- |
| **问题** | 场景三"批量发票部分需审批"无法处理,`ApprovalRequest` 是单一实体,Aggregator 无 `pending_approvals` 字段 |
| **影响** | 批量场景下要么全部审批(低效),要么全部不审批(违规) |
| **修复方案** | Aggregator 输出 `pending_approvals: list[ApprovalRequest]`,审批节点循环处理,支持部分通过部分拒绝 |
| **优先级** | P1 |
| **状态** | ⏳ 待修复 |

### P1-2:置信度阈值策略不完整

| 项 | 内容 |
| :-- | :-- |
| **问题** | 当前阈值硬编码(<0.4 标记,<0.6 提示人工),无拒绝下限、跳过上限、场景化配置 |
| **影响** | 低质量答案仍会返回;政策类问题阈值应更保守但无法配置 |
| **修复方案** | 引入场景化阈值配置(政策类 0.8,factual 类 0.6),<0.2 直接拒绝,>0.9 跳过人工提示 |
| **优先级** | P1 |
| **状态** | ⏳ 待修复 |

### P1-3:动态重规划缺失

| 项 | 内容 |
| :-- | :-- |
| **问题** | Planner 输出静态 plan,执行中 Analysis 发现异常无法追加检索;`route_after_agent` 无 `replan` 路径 |
| **影响** | 复杂场景下任务无法自适应,可能给出不完整答案 |
| **修复方案** | Agent 输出 `needs_replan=True`,路由回 Planner 重新拆解,保留已执行结果 |
| **优先级** | P1 |
| **状态** | ⏳ 待修复 |

### P1-4:知识库运营后台缺失

| 项 | 内容 |
| :-- | :-- |
| **问题** | 文档入库审核、陈旧文档下线、知识库质量度量均未设计 |
| **影响** | 知识库快速腐化,检索质量持续下降 |
| **修复方案** | 入库审核流 + 文档生命周期(草稿/生效/归档/下线)+ 质量度量指标(被引用率/命中率/差评率) |
| **优先级** | P1 |
| **状态** | ⏳ 待修复 |

### P1-5:反馈学习闭环缺失

| 项 | 内容 |
| :-- | :-- |
| **问题** | 用户点踩/点赞无回流机制,RAG 无法持续优化 |
| **影响** | 系统不会越用越准,无法形成数据飞轮 |
| **修复方案** | 反馈采集 → 标注队列 → 评测集扩充 → Prompt/检索参数调优的闭环 |
| **优先级** | P1 |
| **状态** | ⏳ 待修复 |

### P1-6:Prompt 版本管理缺失

| 项 | 内容 |
| :-- | :-- |
| **问题** | Prompt 硬编码在代码中,无版本管理,改 Prompt 需发版 |
| **影响** | 迭代效率低,无法 A/B 测试 |
| **修复方案** | Prompt 模板仓库(LangSmith Hub/自建)+ A/B 测试 + 灰度发布 |
| **优先级** | P1 |
| **状态** | ⏳ 待修复 |

### P1-7:Aggregator 冲突检测逻辑缺陷

| 项 | 内容 |
| :-- | :-- |
| **问题** | knowledge.confidence 与 analysis.confidence 计算方式不同(检索得分均值 vs LLM 自评),不可直接比较 |
| **影响** | 冲突检测误报或漏报 |
| **修复方案** | 统一置信度归一化,或改用"结论一致性"判断(数值是否在相同量级) |
| **优先级** | P1 |
| **状态** | ⏳ 待修复 |

### P1-8:场景二"升级人工"无具体动作

| 项 | 内容 |
| :-- | :-- |
| **问题** | coverage="partial" 时 Aggregator 仅添加文字提示,无创建工单或转人工的动作 |
| **影响** | 用户得不到有效跟进,问题悬空 |
| **修复方案** | coverage="partial" 时,Aggregator 自动调用 ExecutionAgent 创建升级工单 |
| **优先级** | P1 |
| **状态** | ⏳ 待修复 |

### P1-9:Planner 与 RiskClassifier 职责重叠

| 项 | 内容 |
| :-- | :-- |
| **问题** | Planner 让 LLM 输出 risk_level,RiskClassifier 又是独立规则类,二者谁为准不明 |
| **影响** | LLM 误判风险等级可能导致高风险操作绕过审批 |
| **修复方案** | Planner 只输出 operation_type,风险等级由 RiskClassifier 规则强制判定,LLM 不得覆盖 |
| **优先级** | P1 |
| **状态** | ⏳ 待修复 |

### P1-10:审计日志写入失败未处理

| 项 | 内容 |
| :-- | :-- |
| **问题** | 审计日志异步写入失败会丢失审计数据 |
| **影响** | 合规风险,异常事件无法复现 |
| **修复方案** | 本地缓存 + 重试;连续失败触发告警但不阻塞业务 |
| **优先级** | P1 |
| **状态** | ⏳ 待修复 |

### P1-11:递归限制超限无兜底

| 项 | 内容 |
| :-- | :-- |
| **问题** | recursion_limit=25,超限时抛异常无兜底 |
| **影响** | 复杂任务直接报错,用户体验差 |
| **修复方案** | 监控递归深度,接近上限时强制 aggregate |
| **优先级** | P1 |
| **状态** | ⏳ 待修复 |

### P1-12:用户取消任务未处理

| 项 | 内容 |
| :-- | :-- |
| **问题** | 审批等待时用户说"算了",无法中止图 |
| **影响** | 用户无法主动终止,资源浪费 |
| **修复方案** | 用 LangGraph `cancel` API + 前端取消按钮 |
| **优先级** | P1 |
| **状态** | ⏳ 待修复 |

### 5.3 P0-1 复评备注

**优点**:
- 12 类错误枚举覆盖全面
- 副作用(创建工单)失败不阻塞主流程,设计合理
- 兜底后清除 error 状态避免循环

**潜在问题**:
- `ErrorClassifier` 用正则匹配,对中文错误描述的覆盖可能不足,建议补充测试用例
- `FallbackExecutor` 通过 `from app.dependencies import get_fallback_executor` 注入,依赖注入容器未在文档中定义,研发时需明确

### 5.4 P0-2 复评备注

**优点**:
- 用 `Send` API 实现真正的 fan-out
- `wait` 同步点 + `parallel_pending` 计数器机制清晰
- Aggregator 改造支持并行与顺序结果混合

**潜在问题**:
- `merge_parallel_results` reducer 假设 `step_id` 唯一,但若 Planner 输出重复 step_id 会出问题(应在 Planner 校验)
- `route_after_planner_parallel` 返回 `list[Send] | str` 联合类型,LangGraph 条件边的映射表 `{"knowledge": "knowledge", ...}` 如何处理 list 返回值需研发时验证(可能需要返回特殊 key)
- `wait` 节点空操作但会消耗一次递归,需注意 recursion_limit

### 5.5 P0-4 复评备注

**优点**:
- `CompensationRegistry` 注册机制灵活,新工具补偿动作易扩展
- 逆序补偿逻辑正确
- 补偿失败告警人工介入,避免静默失败

**潜在问题**:
- 补偿动作本身可能失败(如 CRM 删除接口异常),当前仅告警但不重试,可能产生孤儿数据
- `batch_id` 依赖 Planner LLM 正确输出,若 LLM 漏标 batch_id 则 Saga 不生效(应有兜底:同一 plan 中连续的 execution 步骤默认归为同批次)
