## 【开场白】(未翻页,站在封面页前)

各位好,我今天汇报的项目叫「Hello,小A」——一个企业知识工作流 Agent。

先用一句话说清楚它是什么:**员工用自然语言,一站式完成知识问答、数据分析和业务执行**。比如销售员问一句"客户 C001 最近什么情况",它查完档案直接生成回答;再说一句"给他发个续约报价邮件",它会先判断——这是外部邮件,高风险,自动挂起送经理审批,批准后才真正发出去。

所以今天 15 分钟,我不只想讲"它能做什么",更想讲三件事:第一,它怎么做**企业级**——权限、审批、降级、断点恢复;第二,这些能力全是**实测验证**过的,不是 PPT 概念;第三,我踩过的**十四个坑**,以及每个坑背后的二阶思考。

## P5 · 技术栈详解

**【建议时长】35s**

**【口播稿】**

技术栈这张表不逐个念,点三个关键职责。

**Milvus** 存 1024 维向量(bge-m3 本地生成),关键设计是按部门建**物理 partition**,权限隔离在存储层就划开了,不是靠查询时过滤兜底。

**Redis Stack** 两个职责:存 checkpoint 快照链——图执行的每个 super-step 都落盘;另外用 ZSET 做滑动窗口限流。注意是 Redis **Stack**,因为 checkpointer 需要 RediSearch 模块,这个坑后面教训页会讲。

**本地 qwen3.5:4b** 是 lite 链路的主力:意图分类、工具选择、答案自评、闲聊判断都在本地跑,实测 0.2-0.3 秒一次,免费而且数据不出内网。

一句话总结:**每个组件存什么、干什么都有明确边界——成本、隔离、状态,三件事各有归属**,不是堆名词。

## P6 · 系统架构总图

**【建议时长】45s**

**【口播稿】**(重点页,可指图)

架构全图就三个节点:**planner 做意图分类和任务分解,条件边用 Send API 并行 fan-out 到三个子 Agent,aggregator 统一汇总**。

先回答最关键的问题:为什么用 LangGraph 显式状态机,而不是 ReAct 自由循环?因为**企业场景里"权限决策发生在哪一步"必须可审计**。ReAct 是模型自己决定下一步的黑盒循环,灵活但不可预测;我们的任务域是封闭的——知识、分析、执行三类——所以把路由写成显式代码:planner 输出 intent,条件边决定去哪,每一步可审计、可断点恢复、可并行。

三个工程细节。**第一,Send fan-out**:条件边返回 list[Send],每个分支携带独立的只读子状态——user_input、request_id、current_subtask、intent 四个字段——**从结构上消除并行写冲突**,结果由 reducer 合并。**第二,executor 必须是 async 节点**:Agent 内部要访问 SQLAlchemy async 引擎,asyncpg 连接绑定事件循环,sync 节点跑在线程池里会报 "Future attached to a different loop"——这是联调真实踩崩过的。**第三,可重置 reducer**:agent_results 空列表重置、非空累加,一个 reducer 同时满足"每轮重置"和"并行累加"两种语义。这一条请记住,教训页还会回来讲它为什么重要。

**【翻页时机】**"还会回来讲"说完翻页。

## P8 · 知识问答

**【建议时长】40s**

**【口播稿】**

第三幕,三大能力逐个展开。先是知识问答,四步链路。

**第一步向量粗排**:bge-m3 把 query 向量化,Milvus HNSW 召回 top_k×4 候选——粗排放大候选池保召回率;过滤条件是部门 partition 加 access_roles 双条件。**第二步精排**:bge-reranker-large 对候选逐对交叉编码打分,取 top-5——reranker 慢,不能对全库用,两阶段就是召回率和精确率的成本折中。**第三步置信度决策**:检索分 ×0.6 加本地小模型自评分 ×0.4,按问题场景(POLICY/FACTUAL/COMPARATIVE)用不同阈值,决定直接答、带提示答、还是拒答。**第四步生成**:本地 qwen 严格基于片段生成,末尾带来源标注。

核心原则再说一遍:**拒答优于编造**——企业知识库给员工一个错的制度答案,代价远高于说"不知道"。

实测数据:冷启动首请求 48 秒(模型加载),稳定后 **14.6 秒**;评测集命中率 **22/22**;整条链路 6 次模型调用,**0 次上云**,全本地完成。

(时间够可加讲)还有个细节:政策场景做了"shared 平局优先"——部门文档和公司共享文档分数差在 0.03 噪声带内时,强制共享原文排前,因为部门文档往往是共享政策的片段副本。0.03 这个阈值来自实测分数分布,不是拍的。

**【翻页时机】**"全本地完成"(或"不是拍的")说完翻页。

## P9 · 数据分析

**【建议时长】35s**

**【口播稿】**

数据分析这页,讲"禁止编造数字"的**工程实现**——注意,不是在 prompt 里求模型别编数字,那是软约束,没用。

三步:**lite LLM 只负责解析分析计划**——metrics、entities、compare、dimensions,输出 JSON;然后 **Python 对数据做真实聚合**,数字全部来自代码计算,数据不足时允许多跳补充,但**最多 2 轮**,这是防无限循环的护栏;最后 primary LLM 把计算结果写成报告,模板里写死"禁止编造数字",LLM 失败就降级成 Markdown 表格直出——用户照样拿到数据。

看下面的例子:对比 C001 和 C002 的累计销售额——北京华信科技两百八十五万、上海拓维贸易一百五十二万、差额一百三十三万。**这三个数是 Python 聚合客户档案 total_revenue 字段算出来的,LLM 只负责把话说圆。**这就是"数字可信"和"表达自然"的职责分离。

**【翻页时机】**"职责分离"说完翻页。

## P10 · 业务执行

**【建议时长】50s**

**【口播稿】**(重点页)

业务执行是安全密度最高的一层,四块设计挨个说。

**第一块,工具选择云端优先**。这里有个反转:高风险操作比如外部邮件,选错工具代价大,所以用云端 deepseek-v4-flash 优先,实测只要 1.2-1.5 秒;低风险常规任务才用本地小模型兜底;最后是关键词映射兜底,还带外部邮件地址纠偏。为什么本地小模型不能挑大梁,后面路由反转页会讲实测证据。

**第二块,RBAC 三防线**。prompt 层:无权工具不注入,模型根本看不到——这层防"无意";执行层:LLM 输出再经 ROLE_TOOLS 显式过滤;工具层:invoke() 里 can_use_tool 终审,越权尝试记 security_violation 审计。**为什么一层不够?因为降级路径不经过 prompt**——LLM 挂了走关键词匹配兜底时,第一层就不存在了,所以必须三道独立防线。

**第三块,Saga 反向补偿**。多工具顺序执行,任一步失败,反向顺序补偿已成功的步骤;QUERY 类无副作用免补偿;**补偿失败不阻断流程**,记 compensation_errors 交运维介入——这是最终一致性,不是 ACID。

**第四块,高风险审批流**。requires_approval 标记的工具不直接执行,自动建审批单,prefill_payload 冻结调用参数;经理批准后服务端同步执行。**但批准不等于放权——这是下一页的核心。**

**【翻页时机】**"这是下一页的核心"说完翻页。

## P11 · 三条降级链

**【建议时长】50s**

**【口播稿】**(重点页,指表格)

第四幕工程亮点。先看可用性的系统解法:这张表是七条链路的降级设计。LLM 主链 DeepSeek v4-pro 挂了就降级本地 qwen,再不行规则匹配拼接;lite 链本地优先、云端 flash 降级;意图分类本地失败云端重试一次,再不行规则关键词;向量检索 Milvus 挂走 BM25 关键词,再不行 PG LIKE;checkpointer 从 Redis 降 PG 再降内存;限流 Redis 挂走内存计数;审计 PG 写不进去写本地文件,连续失败 5 次触发告警。

**一句话:任何 LLM 失败都有非 LLM 的退路,任一依赖故障,用户永远拿得到响应。**

但这页真正想讲的是底下橙色这块——**降级链曾经把"向量检索没生效"这个配置错误掩盖了两个月**。联调前 .env 里 VECTOR_STORE_PROVIDER 实际是 memory,向量检索从未生效,但 BM25 关键词降级兜得太好,从外部看一切正常。

从此我立了一条原则:**降级策略必须配"我在降级"的信号**。当前生效的后端标识——checkpointer_backend、向量 provider——暴露在 /ready 和每一次对话响应里;监控上把"降级次数"当独立指标,因为**降级次数突增,往往比错误率更早告诉你上游出事了**。兜底可以兜可用性,不能兜掉可观测性。

**【翻页时机】**"不能兜掉可观测性"说完翻页。

## P12 · 安全闭环

**【建议时长】50s**

**【口播稿】**(重点页)

安全闭环这页是全场的核心论点:**审批不越权**。

先看左边 RBAC 矩阵:5 角色 × 8 工具。销售员能查客户、查订单、建任务、发内部邮件,但 email_external 标红了——**要审批**;客服能建工单改工单;财务只能查订单;经理和管理员全量。每个角色的工具面一眼可查。

右边是文档侧的命名空间隔离:chunk 带 dept_namespace 和 access_roles 两个标量,按部门物理 partition;检索时双条件过滤——本部门加 shared_company 双匹配,公司级共享文档所有人都能看。**关键是降级链同口径**——这里真实踩过坑:BM25 降级路径当时漏了 dept_namespace 过滤,向量库一挂、走降级,跨部门文档就泄露了。现在过滤条件收敛到统一入口,外加 4 项回归断言长期守护。

底部红卡是三道保证:**第一,执行 context 的 role 和 dept 取自 users 表里发起人的当前角色,不是审批人;第二,执行前预检——审批 pending 期间如果发起人角色被管理员收回,执行会提前失败并记 security_violation;第三,工具层按发起人角色终审,审计里 decided_by 和 executed_as 分开记——谁批的、以谁的身份执行的,事后追责一清二楚。**

一句话总结:**审批的语义是"授权这一次操作",不是"临时获得审批人的权限"——审批系统本身,不会成为提权通道。**

**【翻页时机】**"不会成为提权通道"说完翻页。

## P13 · 状态可靠性

**【建议时长】35s**

**【口播稿】**

状态可靠性,两个机制。

**Checkpointer 断点恢复**:图执行的每个 super-step——planner 后、每个 executor 后、aggregator 后——自动落 Redis 快照;thread_id 就是 session_id,同一会话天然跨进程恢复。实测场景:**杀掉 API 进程、重启、用旧 session 续聊,checkpoint 完整恢复**,115 秒长链路跑通。而且这个测试里专门核对了恢复后的 Milvus 余弦分 0.57/0.50——**证明恢复后检索是真走向量库的,不是降级兜底在假装正常**。这就是前面说的"验证主路径真的在走"的联调用例。

**Saga 反向补偿**,右边是真实实例:建任务成功、发邮件失败——反向补偿自动取消已建的任务,任务状态置为 compensated,用户看到的是"任务已创建但通知失败,已自动取消"。

补偿失败怎么办?不阻断,记入 compensation_errors 返还运维。原则再强调一遍:**邮件发出去了只能发撤回信,分布式系统没有真回滚——宁可"补偿失败 + 告警 + 人工介入",也不假装能完美回滚。**

**【翻页时机】**"不假装能完美回滚"说完翻页。

## P14 · 可观测与审计

**【建议时长】25s**

**【口播稿】**

工程亮点最后一块,可观测三件套。

## 【Q&A 应对提示】(最可能被问的 6 个,附回答思路)

1. **为什么选 LangGraph 而不是 AgentExecutor / AutoGen?**
   → AgentExecutor 是 ReAct 黑盒循环,权限决策点不可枚举、不可审计;AutoGen 路由靠多 Agent 对话涌现,保证不了"高风险操作一定过审批"这种硬约束。我们任务域封闭(知识/分析/执行),用显式状态机换可预测、可断点恢复、可并行——放弃的是应对开放任务的灵活性,用不上。

2. **QPS 翻 100 倍,哪里先崩?**
   → 按顺序:云端 LLM 的 rate limit 和成本(最先,且是外部约束)→ uvicorn worker 被 40-110s 长请求占满 → Milvus 单机内存 → Redis checkpoint 存储。对策:本地模型承接更多 + 请求级缓存;SSE + 水平扩 worker;Milvus 集群或缩维度;checkpoint 加 TTL。要点:**先崩的是外部依赖,不是自己的服务。**

3. **降级链会不会掩盖配置错误?**
   → 会,真实踩过:VECTOR_STORE_PROVIDER=memory,向量检索空转两个月,BM25 降级兜得太好。修复两条:当前生效后端暴露在 /ready 和每次响应;联调专门设计"验证主路径真的在走"的用例(核对 Milvus 余弦分)。原则:**降级策略必须配"我在降级"的信号。**

4. **多轮上下文怎么做的?**
   → 已落地轻量版:run_graph 入口从 checkpoint 快照链取最近 5 轮 (message, answer) 对,注入 planner/knowledge 现有槽位(不改模板);knowledge 检索前做指代消解——query 含"它/这/那"时拼接上一轮用户消息再做 embedding。实测"销售提成政策是什么"→"那它的折扣呢"承接正确。边界:无压缩、5 轮封顶,摘要压缩是预留设计。

5. **工具是 Mock,这套东西有用吗?**
   → Mock-first 是有意识策略:8 个工具的 pydantic schema、ToolResult、compensation_data 完全对齐真实 API 契约,切真实系统只需子类覆盖 _execute。价值在于 RBAC/Saga/审批/注入防护这些安全链路在真实系统缺位时就完成了端到端联调——如果等有真实 CRM 才开发,安全逻辑和业务联调挤在一起,出问题分不清是哪层。

6. **审批人批准了,能不能代办执行?**
   → 不能,这是设计。批准后仍按发起人角色过 RBAC 终审:执行 context 取 users 表发起人当前角色、pending 期间角色被收回会提前失败记 security_violation、审计分离记录 decided_by 和 executed_as_*。审批的语义是"授权这一次操作",**审批系统本身不会成为提权通道**。

## 【备选追问】(有时间再展开的 4 个)

7. **怎么证明 Agent"好"?**
   → 三层证据:离线评测集四指标(命中率/覆盖率/置信度分布/延迟);17 项联调含负例;在线审计 + like/dislike 反馈回流,dislike 自动生成知识候选草稿,人工审核后才进库——未审核内容不进库,这是质量闸。

8. **prompt 改了怎么保证不变差?**
   → 11 个 prompt 全部进 prompt_versions 表(draft/active/archived + traffic_weight);A/B 用 md5(user_id+name)%100 确定性分流——同一用户永远命中同一版本,效果按版本号聚合 confidence/feedback 对比;回滚 = 激活旧版本。DB 挂了降级代码内置默认,业务不中断。

9. **长请求 40-110s 怎么取消?**
   → session_id → asyncio.Task 注册表,/chat/cancel 触发 task.cancel();前提是 LLM 调用全面 ainvoke 化,取消信号在 await 点即时生效——实测 token 正在流出时取消,流以 cancelled 事件收尾,sessions 落 cancelled。边界:注册表是进程内的,多实例要 Redis pub/sub,这是 YAGNI 预留。

10. **这个系统离生产上线还差什么?**
    → 三件事按序:压测拿并发基线 → UAT + 安全实测(prompt 注入攻击面、模糊测试)→ prompt A/B 效果数据积累。技术债里 pymilvus 3.1 迁移是硬 deadline,其余是体验项。
