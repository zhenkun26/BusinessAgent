第一幕 · 缘起

企业内部知识,为何总问不到、找不到、控不住?

三个真实痛点,催生了这个项目。

01

知识分散

制度、流程、业务知识散落在各类文档,员工查询靠问人、翻文档,效率低且口径不一。

02

系统割裂

查客户、发邮件、建工单要在多个系统间手工切换,每个动作都要重新登录、复制粘贴。

03

风险失控

高风险操作(如外部邮件)无审批拦截,越权访问难以防范,出了事无法追溯。

价值主张
一个 Agent,三类能力,企业级安全闭环 —— 让员工用一句话完成原来跨五系统的工作。

第四幕 · 工程亮点

状态可靠性:杀进程重启,会话不丢

Checkpointer 断点恢复

每个 super-step(planner 后 / 各 executor 后 / aggregator 后)自动落 Redis 快照。thread_id = session_id,同会话天然跨进程恢复。

实测:杀 API 进程重启 → 旧 session 续聊 → checkpoint 完整恢复 → 本轮检索真实走 Milvus(余弦分 0.57/0.50)→ 耗时 115s 长链路通过

Saga 反向补偿

多工具顺序执行,任一步失败反向补偿已成功步骤;每个 ACTION 工具实现 compensate,执行时记录 compensation_data。

实例:[建任务✓ → 发邮件✗] → 反向补偿:取消任务 → 任务 status=compensated → 用户看到「任务已创建但通知失败,已自动取消」

补偿失败怎么办?

补偿失败不阻断流程,记入 compensation_errors 返还运维 —— 这是最终一致性不是 ACID。邮件发出去了只能发撤回信,分布式系统没有真回滚。原则:宁可"补偿失败 + 告警 + 人工介入",也不假装能完美回滚。

第六幕 · 取舍与教训

关键取舍:放弃了什么,什么情况下会改

每个"选"都对应一个"弃",这才是工程决策的本质。

显式 StateGraph —— 路由可预测、权限可审计、断点可恢复
ReAct 自由循环 —— 应对开放任务的灵活性(任务域封闭,用不上)
Mock-first —— 契约对齐真实 API,安全链路提前两周端到端联调
等真实系统 —— 数据真实性(测不出真实脏数据与延迟分布)
本地 qwen3.5:4b 承担高频低风险任务 —— 成本降 40%+,数据不出内网,闲聊 5.9s 零云端

第六幕 · 取舍与教训

两次路由反转:路由策略是测出来的,不是想出来的

两次"凭印象"的模型路由设计,都被实测数据推翻。

2026-07-26 · 路由反转 #1
lite 层从"云端 flash 优先"反转为"本地优先"

曾误判本地慢是 GPU 争用迁云端,后实测发现真因是 ChatOpenAI 走 Ollama /v1 端点时 extra_body={"think": False} 被忽略,模型照生成 thinking token(自评单次 44-94s)。迁移 ChatOllama + reasoning=False 走原生 /api/chat 后,本地 0.2-0.3s/次,快于云端 flash(8.7-18.1s),lite 层反转为本地优先、云端 flash 降级。

2026-07-28 · 路由反转 #2
execution 工具选择反转为"云端 flash 优先"

本地 4B 会返回"合法 JSON 但选错工具"(实测发外部邮件话术稳定只选 query_customer,漏掉 send_email_external),此时旧回退(仅本地失败/返回空才上云)不触发,审批单建不出来。改候选链 云端 flash → 本地 → 关键词 后实测建单恢复,云端 flash 仅 1.2-1.5s/次,成本≈0。教训:工具选择是 4B 最弱环节,"选错工具"比"返回空"更危险。

共同教训:模型路由不能凭印象设计 —— 延迟要实测(本地"慢"的真相是协议适配层抽象泄漏)、正确率要回归("返回合法 JSON"不等于"选对了工具")。候选链不只看"是否失败",还要看"是否正确"。

第六幕 · 取舍与教训

十四个深刻教训:二阶思考比修复更重要

坑 1 · 最有讲头

降级链掩盖配置错误

联调前 RAG 一直"能出结果",但 VECTOR_STORE_PROVIDER 实际是 memory,向量检索从未生效 —— BM25 关键词降级在兜底。从外部看一切正常,实际上向量检索空转两个月。

二阶思考:任何兜底机制都是双刃剑 —— 它消化故障的同时也在消化信号。降级策略必须配"我在降级"的声明,监控把"降级次数"作为独立指标。
坑 2 · 组合状态盲区

operator.add reducer + checkpoint = 跨轮污染

断点恢复后续聊,aggregator 汇总出了上一轮的结果。根因:默认 reducer 语义是"追加",checkpoint 恢复把上轮 agent_results 带回来,新一轮写入追加在残留上。

二阶思考:框架默认值和业务真实语义不一致时,默认值是最危险的地方 —— 它在单轮测试里永远正确,只在"恢复+新一轮"的组合场景爆炸。组合状态 × 生命周期是测试盲区。
坑 3 · 隐性契约

同步节点跨事件循环调 DB

executor 内审批建单报 "Future attached to a different loop"。根因:asyncpg 连接绑定主事件循环,sync 节点跑在线程池,线程里 asyncio.run 建新 loop 去用旧 loop 的连接。

二阶思考:async 生态里"哪个对象绑定哪个 loop"是隐性契约,单元测试(单 loop)永远测不出。并发模型必须在架构评审时显性化,画清楚每个资源归哪个 loop。
坑 4 · 选错工具比返回空更危险

本地小模型返回合法 JSON 但选错工具

外部邮件场景,本地 qwen3.5:4b 返回合法 JSON,却只选了 query_customer 漏掉 send_email_external —— 旧回退只在"本地失败/空响应"时上云,"选错工具"不触发回退,导致外部邮件突然不送审、绕过审批。根因:本地小模型"能选对工具"和"能填对参数"是两个能力层级。

二阶思考:候选链不能只看"是否失败",还要看"是否正确"。高风险操作改为云端 deepseek-v4-flash 优先 → 本地 qwen 兜底 → 关键词兜底。实测云端 flash 1.2-1.5s,比本地还快。
坑 5 · 序列化边界

checkpoint 反序列化类型漂移

断点恢复后 Aggregator 访问 AgentResult.success 崩溃;流式 sources 全部 score 0.000、标题与分区为空;多轮历史派生时 user_input 取不到 message 字段。三次独立场景、同一类问题反复出现。根因:LangGraph checkpoint 以 JSON 存储,pydantic 模型反序列化后变成 dict;Redis saver 不复活自定义类,部分字段还以 LangChain 序列化信封 {"lc","type":"constructor","kwargs":{...}} 形态存在。

二阶思考:任何跨序列化边界的类型契约都不可信。生产方"我是 pydantic 模型"的保证在序列化那一刻就失效了,消费方防御比生产方保证更可靠。修复:消费入口 model_validate 或按 dict 兼容访问,跨 checkpoint 边界取数必须先解 kwargs 层。单元测试(单进程内对象直传)永远测不出。
坑 6 · 安全不变量漂移

降级路径绕过部门隔离(跨部门泄露)

P2 调研发现 BM25 降级检索只过滤了 is_active 和 access_roles,漏了 dept_namespace —— 向量检索挂掉走降级时,跨部门文档会泄露给无权用户。根因:主路径的过滤逻辑实现向量检索层里,降级路径是后来补的,安全条件没有跟着复制一遍。代码评审看不出来,因为两条路径各自都"看起来合理"。

二阶思考:安全不变量必须独立于实现路径。"部门隔离"应该是一条无论走哪条检索路径都成立的不变量,最好的结构是把过滤条件收敛到一个构造函数,所有路径调用它,而不是每条路径各写一份。靠 run_p2_namespace.py 4 项断言(含降级路径)做长期守护。
坑 7 · ORM 升级盲区

SQLAlchemy 2.x 原生 SQL 扫盲区

① 服务起不来,conn.execute("SELECT 1") 直接报错(阻塞性);② 待审批列表 500,JSONB 列 = ANY(jsonb_col) 语法 PG 不支持。根因:SQLAlchemy 2.x 强制要求原生 SQL 用 text() 包装;JSONB 数组成员判断必须用 jsonb_col ? 'value' 或 @> 操作符。ORM 托管的查询有版本兼容层,手写 SQL 没保护。

二阶思考:升级 ORM 大版本后,原生 SQL 是扫盲区 —— ORM 把日常 CRUD 的兼容性吃掉了,让开发者误以为"升级没影响",但手写 SQL 部分仍是裸 SQL。升级 checklist 里必须有"全量 grep 原生 SQL + JSONB 操作符"。这个坑是阻塞性的(服务起不来),必须在升级前回归。
坑 8 · 镜像默认行为依赖

Redis 镜像 ENTRYPOINT 的隐性依赖

checkpointer 启动报 FT._LIST unknown command;换 redis-stack-server 后又出现"容器活着但 RediSearch 模块没加载"。根因:① redis:7-alpine 不含 RediSearch 模块,checkpointer 需要 FT.* 命令;② docker-compose 里覆盖 command: 会跳过镜像默认的 ENTRYPOINT 模块加载链,必须显式 --loadmodule redisearch.so rejson.so。

二阶思考:镜像的默认行为(ENTRYPOINT/CMD 链)也是依赖。覆盖 command 时,继承关系要搞清楚 —— 不能只看"容器活着"。验证手段要直抵能力本身(redis-cli FT._LIST 验证索引存在),而不是"容器状态 healthy"。"healthy"只代表进程活着,不代表业务能力可用。
坑 9 · 工程解法 vs prompt 祈求

LLM 输出格式宽容解析

① SendEmailSchema.to 拒收单字符串(LLM 高频输出 str 而非 [str]);② 审批摘要把 list 逐字符 join 了(["a","b"] → "['a', 'b']" 当字符串处理);③ 收件人参数被 LLM 猜成 recipient/content 而非 to/body。根因:prompt 里写"必须输出数组"只能降低概率,不能消除 —— LLM 输出格式永远有抖动。schema 层严格校验直接拒绝,导致正常请求失败。

二阶思考:对 LLM 输出要"宽容解析、严格校验、默认值兜底"。prompt 是软约束,pydantic validator 是硬约束 —— 把格式归一化(单 str 自动包装为 list、显式 null 走默认值)做在 schema 层,而不是反复改 prompt 求模型配合。凡是能用代码兜底的格式问题,都不要靠 prompt 解决。
坑 10 · 过度容错

Aggregator 错误兜底掩盖友好提示

RBAC 拒绝时用户看到"处理失败:未知错误",而不是"您的角色(customer_service)无权执行所需工具" —— Agent 精心构造的友好拒绝被兜底逻辑覆盖。根因:兜底逻辑一律用 error 字段拼装回答,而 Agent 已经返回了带友好话术的 output.answer;兜底没区分"有信息"和"无信息"两种情况。

二阶思考:兜底应该兜"没有信息"的底,而不是覆盖"已有信息"。分层回答要分清给谁看 —— Agent 的友好话术是产品体验的一部分,兜底的"未知错误"是诊断信息,二者优先级不能反。修复:优先保留 Agent 自带回答,仅无回答时才用错误兜底。容错要把"已有有效输出"和"真失败"分开。
坑 11 · 抽象泄漏误诊

ChatOpenAI 走 Ollama /v1 端点忽略 extra_body

本地 qwen3.5:4b 自评单次 44-94s、闲聊判断 ~4.4s/条,一度判断为"GPU 争用"迁到云端 flash;后实测发现是 ChatOpenAI 走 Ollama /v1/chat/completions 端点时 extra_body={"think": False} 被 Ollama 忽略,模型照生成 thinking token,所有时间烧在隐藏思考上。根因:OpenAI 兼容端点是社区适配层,不是 Ollama 原生协议。

二阶思考:"对症下药的药"可能治的是错症。第一次诊断"GPU 争用"是基于现象的合理推断,但根因在协议适配层 —— 这层抽象泄漏(OpenAI 兼容端点 ≠ OpenAI 协议语义)只有实测隐藏 token 才能发现。改用 ChatOllama + reasoning=False(走原生 /api/chat)后,自评 65.8s→0.23s、闲聊 4.4s→0.27s。性能问题根因诊断必须有"白盒证据"。
坑 12 · 模型能力迁移暴露隐性依赖

工具选择 prompt 不含参数 schema

/ui 里「给客户 C001 创建回访任务并发内部邮件通知经理」连续报"处理失败";本地 qwen 把 to/body 猜成 recipient/content,漏填必填的 title/assignee,pydantic 校验直接失败。此前这类用例能过,是因为本地恰好返回空 → 云端 flash 重试接管(云端按参数名惯例猜得对)。根因:工具选择 prompt 只注入工具名/描述/类别,不含参数 schema。

二阶思考:lite 本地优先之后,凡依赖"模型猜约定"的环节都要把约定显式化。云端大模型之所以"好用",部分原因是它内化了大量参数命名惯例(隐性约定);一旦切到能力更弱的小模型,这些隐性约定必须显式注入 prompt(字段名+必填标记+字段描述)。修复:_param_spec() 从 model_fields 生成参数规格注入 {tools} 槽;assignee 改 Optional 缺省回填发起人。
坑 13 · Prompt 定义完整性

意图分类 prompt 漏定义导致路由错误

「查询订单 ORD-2026-001 的详情」被路由到知识问答,回答"知识库未覆盖" —— 明显错误路由。根因:意图分类 prompt 的 data_operation 定义只写了"创建/更新/删除",没覆盖"查询业务记录";4B 小模型把"查询"动词归到 knowledge_qa。同时本地分类失败时没有运行时回退,直接吃下了错误分类。

二阶思考:Prompt 中的枚举定义是分类的"边界" —— 少写一项,模型就把该类的样本全部错分到相邻类。规则关键词兜底(RULE_KEYWORDS)也必须同步更新,否则 prompt 修了、兜底还是错的。Prompt 工程的"定义完整性"比"措辞精妙"更重要,且 prompt 与兜底规则是两个事实源,改 prompt 必须同步改规则。
坑 14 · 数据卫生底线

入库脚本不幂等导致 collection 膨胀

反复执行入库脚本后,Milvus collection 从 22 实体膨胀到 116 实体,问答 sources 被同一文档的重复 chunk 挤占(实测 top-5 里三个"销售政策")。根因:run_w9_milvus / run_eval --ingest / app.rag.ingest 三条入库路径均不做幂等去重,反复执行就追加。Milvus 不像 PG 有唯一约束,doc_id 重复不会报错。

二阶思考:入库脚本的幂等性是数据卫生的底线。开发期反复执行是常态,如果脚本不是幂等的,数据会悄悄污染检索质量 —— 而且这种污染不会被功能测试发现(检索"能出结果"),只有召回质量回归(run_eval 命中率/score 分布)才能发现。修复:init_milvus(recreate=True) drop 重建。数据写入路径必须有"幂等性测试"。
