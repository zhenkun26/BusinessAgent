## Context

现状见 proposal.md 的 Why。关键约束：UAT 与安全测试挂起（ISSUES I-02 open，现象为"真实用户验收与 Prompt 注入攻击面未实测"）；自动化回归基线已就绪（`enterprise-agent/tests/` 18 个测试文件、58 个用例全绿）；使用案例手册（`docs/30-guides/使用案例手册.md`，v1.4）已有 17 章手工全流程与 9X 跨部门协作场景，可直接作为 UAT 场景素材；SLA 达标线由 `production-readiness` 规格承载（可用性 ≥99.5%、p95 ≤2s 等初值），压测与备份恢复演练证据由 `load-test-and-dr-drill` change 产出；当前为单机 Docker Compose 部署（docker-compose.prod.yml），灰度只能在用户范围维度放量，没有多套部署环境；文档体系遵循六大层规范，ROADMAP/DECISIONS/ISSUES 各为单一事实源。

## Goals / Non-Goals

**Goals:**
- 把 UAT、灰度、上线门槛三类契约冻结为 `release-management` 正式规格，让"能否全量上线"从口头约定变为可逐项核对、可复核的判定流程。
- UAT 场景素材最大化复用使用案例手册，不另起炉灶写一套平行用例库。
- 门槛检查单的前置证据全部指向既有单一事实源（测试报告、压测报告、演练记录、DECISIONS、ISSUES），不新建证据文档体系。

**Non-Goals:**
- 不改动任何业务代码与部署配置，不引入灰度发布的技术设施（如流量染色、多实例部署）。
- 不在本 change 中执行压测、演练或渗透测试本身（`load-test-and-dr-drill`、`security-hardening-plus` 承接），只定义门槛与证据要求。
- 不追求引入发布管理平台/工具，检查单与记录用 Markdown 承载即可。

## Decisions

### 1. UAT/灰度/门槛合并为一个 `release-management` 规格，而非三个规格

三者同属"发布决策链"（验收 → 灰度 → 放行），生命周期一致且强顺序依赖：UAT 是灰度的前置，灰度结论是门槛检查单的一项证据。合并为一个规格可让放行判定在同一契约内闭环。

备选：拆成三个独立规格。否决：检查单必然引用灰度结论，灰度必然引用 UAT 通过标准，拆开只会增加跨规格同步负担，与 production-readiness 合并三类契约的决策逻辑一致。

### 2. UAT 场景以使用案例手册为素材库，按"角色 × 场景"矩阵组织

手册已有 17 章 curl 版 + 前端版 F1-F14 全流程，含 9X 跨部门协作场景（VIP 跟进、退款争议、紧急 Bug、新客户首单）与 10 个种子用户（5 角色 × 4 部门）。UAT 计划按角色（销售/客服/财务/经理/管理员）× 六类场景（知识问答、命名空间隔离、数据分析、工具执行、审批流、跨部门协作）组织矩阵，每个格子引用手册章节号作为执行脚本，避免另写一套会过期的用例。

备选：从零编写独立的 UAT 用例文档。否决：手册已与代码实测状态对齐（v1.4 对应 v1.2.0），重写只会制造两份需要同步的事实源。

### 3. 灰度在用户范围维度放量，不做技术流量切分

当前为单机 Compose 单实例部署，没有多实例/流量染色基础设施；灰度按用户范围放量：单部门试点（建议销售部，业务场景最全）→ 多部门（+客服/财务）→ 全员。固定观察窗口为 G1 1 周、G2 1 周、G3 2 周，最短总观察期 4 周；如需延长，必须在 `DECISIONS.md` 留痕，指标口径直接引用 `production-readiness` 的 SLA。回滚路径为"停止放量 + 回退到上一稳定版本镜像（docker compose 回滚 image tag）+ 数据备份可用"，不承诺秒级回滚。

备选：保留每级 1-2 周并将 G3 设为 2 周以上。否决：阶段上限无法与总观察期 2-4 周口径一致，不能形成可排期的 GATE-06 证据。另一个备选是先建 K8s 多实例再做技术灰度；同样否决：评审已将 K8s 启用时点列为待评估项（DEPLOY.md:418-433 有判断标准），为灰度而提前上 K8s 是本末倒置。

### 4. 门槛检查单六项与评审定义一一对应，证据引用前置 change 的产物

检查单六项（回归全绿/压测达标/P0/P1 清零/权限与渗透测试/备份恢复演练/灰度稳定）逐项要求证据引用：回归 → CI 与 `tests/` 报告；压测/演练 → `load-test-and-dr-drill` 产出的报告与 RTO/RPO 实测记录；安全 → 渗透测试报告（I-02 的安全测试部分）；灰度 → DECISIONS 中的灰度结论。本规格只引用这些概念，不对 `production-readiness` 或其他规格写 delta。

备选：把 SLA 目标值复制进本规格。否决：违反单一事实源，SLA 口径变更时两处会漂移。

## Risks / Trade-offs

- UAT 依赖真实用户投入，排期不可控 → 场景矩阵按角色裁出最小可执行集（每角色 3-5 个核心场景先行），允许分批验收；通过标准中明确"核心场景全部通过"为硬门槛，扩展场景允许遗留非 P0/P1 问题。
- 灰度观察期最短 4 周拉长整体上线周期 → 明确标注 4 周是硬下限，不压缩；如需延长必须记录理由；观察期内并行推进真实系统集成（阶段二 change），不占串行关键路径。
- 单机部署的回滚能力弱（无蓝绿，靠镜像 tag 回退 + 备份） → 回滚触发条件写得更保守（突破 SLA 或 P0/P1 即回退），并把"备份可用"列为回滚路径的前提，与演练证据互相印证。
- 前置证据依赖其他 change 按时完成 → tasks 中把"确认前置 change 归档状态"列为显式步骤，检查单项缺证据时阻止放行而非放宽。

## Migration Plan

无代码迁移。执行顺序：确认前置 change（production-readiness-baseline、load-test-and-dr-drill）归档状态 → 起草 UAT 计划（场景矩阵）→ 评审并执行 UAT（可分批）→ 收口 ISSUES I-02 → 起草灰度方案并评审 → 按方案执行灰度观察 → 逐项核对门槛检查单 → 放行结论落 DECISIONS。

- 灰度期间 Prompt A/B 流量功能（手册 13.3）是否可用于答案质量的灰度对照？倾向可用但非必需，作为灰度观察的补充手段，不写入硬门槛。
