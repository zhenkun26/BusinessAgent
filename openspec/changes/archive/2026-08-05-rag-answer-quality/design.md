## Context

现状见 proposal.md 的 Why。关键约束：评测基础设施已存在（`eval/run_eval.py` 支持 `--ingest` 自动入库评测，输出 top-k 命中率、MRR、关键词覆盖率与分场景/分难度统计，落盘 `eval/results/latest.json`）；样例文档在 `eval/sample_docs/`（销售政策、财务报销制度、售后服务政策、产品手册、常见问题FAQ 及 dept_sales/dept_finance 两个部门目录）；当前评测集的"关键词覆盖率"口径是 expected_keywords 在 **检索 chunk** 中的出现比例，尚未触达生成环节；生成链路在 `app/rag/`（retriever、reranker、llm、degradation），评测脚本目前只调用 `EnterpriseRAGRetriever`，不经过 LLM 生成。

## Goals / Non-Goals

**Goals:**
- 评测集扩充至 ≥100 条并覆盖多业务域与对抗性样本，样本格式沿用 eval_set.json 现有字段（query_id/query/ground_truth_doc/ground_truth_section/expected_keywords/scene/difficulty）。
- 评测增加答案层指标：对每条样本实际调用生成链路，统计 expected_keywords 在最终答案中的覆盖率，与检索层覆盖率并列输出。
- 对低覆盖样本逐条归因（检索未命中 / 上下文组装遗漏 / 生成遗漏），形成分类统计后再修 prompt 或组装策略。
- 把评测集规模、答案覆盖率目标（≥0.85）、回归频率冻结进 knowledge-operations 规格。

**Non-Goals:**
- 不更换嵌入/重排序模型与向量库（bge-m3、bge-reranker、Milvus 维持现状）。
- 不引入 LLM-as-judge 等主观评分体系，本轮只用可机械校验的关键词覆盖率口径。
- 不做检索层指标的进一步提升（已满分），不做在线 A/B 评测。

## Decisions

### 1. 沿用关键词覆盖率口径做答案层度量，而非引入新评分体系

现有评测已用 expected_keywords + 覆盖率的机械口径，扩展到答案层只需对生成结果做同样的字符串匹配，口径一致、可复现、可回归对比。

备选：引入 LLM-as-judge 或人工评分。否决：本地 qwen3.5:4b 评分稳定性差、人工评分不可回归，且学习项目不需要那么重的体系；机械口径足以暴露"检索命中但答案漏关键词"这一核心问题。

### 2. 答案层评测复用 run_eval.py 扩展，而非新建评测脚本

在 `eval/run_eval.py` 中增加生成环节调用（走 `app/rag/` 的生成链路），EvalReport 增加 answer_keyword_coverage 字段并与既有检索层 keyword_coverage 并列；结果文件沿用 `eval/results/latest.json` 格式向后兼容扩展。

备选：新建独立脚本。否决：检索与答案两层指标必须在同一次运行、同一份检索结果上对比，分开跑会引入检索抖动导致的归因误差。

### 3. 失效模式按"检索未命中 / 组装遗漏 / 生成遗漏"三分类

归因逻辑可机械化：检索未命中（doc_match=false）→ 检索问题；检索命中但关键词不在 top-k content → 组装/截断问题；关键词在上下文中但不在答案 → 生成/prompt 问题。先跑分类统计再决定修复点，避免"拍脑袋改 prompt"。

备选：直接调 prompt 看效果。否决：无法区分失效环节，容易改了 A 环节被 B 环节抵消，回归不可解释。

### 4. 评测集扩充以既有样例文档为蓝本，多域样本需先补样例文档

现有 5 份样例文档支撑 22 条样本；扩充至 100 条需要为售后、产品、FAQ 及部门目录文档补写样本，必要时新增少量样例文档（如人事、IT 域）。对抗性样本（无答案拒答类）的 ground_truth 标注为"预期拒答"，覆盖率指标对这类样本单独统计，不计入答案覆盖率分子。

备选：一次性虚构 100 条不进库验证。否决：样本必须与真实入库文档对应，否则检索命中率失真。

### 5. 目标值定为答案层平均关键词覆盖率 ≥0.85，回归基线以本 change 完成时的实测值为准

当前检索层覆盖率 0.606，答案层尚无数据；0.85 是参考检索层满分、留出生成损耗余量的初值，本 change 完成后以实测值建立回归基线，后续 change 不得使基线下降。

备选：目标直接定 1.0。否决：生成环节存在合理转述（如"24小时"答成"一天内"），关键词口径下 1.0 不现实，会倒逼为匹配关键词而堆砌原文。

## Risks / Trade-offs

- 关键词覆盖率口径对同义转述不公平（答对但没用原词会被判未覆盖）→ 在失效模式分析中人工抽查低覆盖样本，区分"真漏答"与"口径误伤"，必要时修订 expected_keywords 而非放宽目标值。
- 评测集扩充到 100 条工作量大且易注水 → tasks 中要求每条样本先入库验证检索可达，对抗性样本单独标注，评审时抽查样本与文档的对应关系。
- 答案层评测引入 LLM 调用，评测耗时与成本上升（当前平均延迟约 1049ms/条，100 条约 2 分钟）→ 可接受；回归评测频率限定为 RAG 链路变更时触发，不接入每次提交。
- 生成链路调用依赖本地 Ollama/DeepSeek 可用性 → 评测脚本需处理生成失败并标记样本状态，失败样本不计入覆盖率分子分母。

## Migration Plan

无线上迁移。执行顺序：失效模式分析先行（对现有 22 条跑答案层评测并归因）→ 扩充评测集至 ≥100 条（含补样例文档与入库验证）→ 按归因结论修复 prompt/组装策略 → 全量回归并建立基线 → 归档规格。

## Open Questions

- 对抗性"无答案拒答"样本的判定口径：以答案中包含拒答/澄清特征词为准，还是要求检索层不命中？倾向以前者为准（系统应先检索再据上下文判断），实施时按实际生成行为确定。
- 答案层目标值 0.85 是否在分场景上差异化（如 inferential 场景放宽）？待首轮 100 条实测数据出来后在评审中确认。
